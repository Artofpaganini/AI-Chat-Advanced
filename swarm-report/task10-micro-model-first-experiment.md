## Задача

Двухуровневый инференс: дешёвый классификатор отсекает большинство запросов до вызова большой LLM.
Уровень 1 - micro-model со структурированным результатом и статусом уверенности.
Уровень 2 - LLM только при `UNSURE` / низкой уверенности / битом формате.
Прогнать 20-30+ запросов (простые, пограничные, сложные), замерить отсечку, число вызовов LLM, latency.
Оформить как соседние задачи челленджа. `RESULT.md` - главный файл, человеческим языком.
Пользователь потом руками проверяет работу в самом приложении.

## Принятые решения

| Развилка | Выбор | Обоснование |
|---|---|---|
| Предметная задача | триаж на 4 маршрута (`EMERGENCY` / `DOCTOR_SOON` / `SELF_CARE` / `OFF_TOPIC`) | корпус уже есть: `task7/data/train_triage_full.jsonl` 1019 примеров + `cases.jsonl` 50 кейсов с группами clean/borderline/noisy; даёт прямую сравнимость с task7/8/9 |
| Micro-model | TF-IDF (word 1-2 + char 3-5) + softmax-регрессия, **чистый stdlib Python 3.9** | в системе нет ни numpy, ни sklearn; ставить пакеты в окружение пользователя нельзя; веса тривиально переносятся в Kotlin |
| Где крутится в проде | **on-device Kotlin**, веса в `composeResources` | ручная проверка без поднятия сервера, отсечка честная - сети нет вообще |
| Fallback | `deepseek-v4-flash`, как в task8 | сравнимость цены и точности |
| Confidence | `max softmax` + `margin` (top1 - top2), два порога | одного порога мало, margin ловит случай «две метки почти равны» |
| Асимметрия | `EMERGENCY` от micro-model всегда эскалируется | цена пропуска несопоставима с ценой лишнего вызова, линия задач task7-9 |

## Как пользователю проверить руками

1. Настройки, тумблер «Micro-model first» включён (дефолт).
2. Бытовой вопрос -> ответ мгновенно, без сети, бейдж `локально · SELF_CARE · <conf> · <N> мс`.
3. Тревожный вопрос -> облачная задержка, бейдж `облако · UNSURE <conf> -> <маршрут>`,
   при подъёме суффикс `(поднято с <исходный>)`.
4. Случай удержания: бейдж `облако · UNSURE <conf> -> EMERGENCY (экстренный маршрут удержан вопреки <X> от LLM)`.
5. Счётчик в шапке «Локально обработано: X из Y · сэкономлено вызовов LLM: X».
6. Выключить тумблер -> всё уходит в облако, бейджа локальной обработки нет.

## Главная находка и правка контракта

За 81 эскалацию большая модель **ни разу не подняла** тяжесть маршрута: 48 согласий, 33 понижения, 0 повышений.
Правило «вердикт LLM побеждает» означало, что fallback умеет только облегчать. Через него ушли три верно найденных
`EMERGENCY` (`borderline_06`, `borderline_08`, `borderline_11`). Каскад оказался хуже обоих своих уровней:
micro ловит 12 экстренных из 13, LLM 10 из 13, каскад 9 из 13.

Правило противоречило принципу из `task7/SPEC.md:8-33` - несимметричная цена ошибки, при сомнении маршрут
поднимается вверх. Дефект в контракте, написанном оркестратором, не в работе агентов.

Исправлено: `WEIGHTS_FORMAT.md` раздел 5.1 - `final_route = более тяжёлый из (micro, llm)`.
LLM может подтвердить или поднять, понизить не может.

**Честная оговорка:** правило изменено после того, как числа были увидены. Поэтому меряется отдельным живым
прогоном `cascade_max`, помечается в отчёте, и для настоящей проверки нужен свежий набор кейсов, которого нет.
В приложении применяется по цене ошибки, а не по метрике.
