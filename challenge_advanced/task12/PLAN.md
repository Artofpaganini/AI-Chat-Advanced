# PLAN - косвенная инъекция промпта

Ход работы по task12. Что делаем, в каком порядке, что берём готовым из task11 и раньше.

---

## 1. Идея

Task11 атаковал системные промпты текстом, который сам пользователь пишет в поле ввода. Здесь
пользователь ни при чём - вредоносный текст сидит в данных (переписка, документ, веб-страница),
которые пользователь просит обработать. Вопрос замера: держится ли анти-инъекционный блок,
укреплённый по итогам task11 (`DEFENSE_HARDENED` стал боевым текстом в `DeepSeekDefaults.kt`),
против инъекции, которая приходит не сообщением, а данными.

## 3. Порядок шагов

1. **`ATTACK_CONTRACT.md`.** Три вектора, пять приёмов сокрытия, пять детекторов, три слоя защиты
   по заданию. Заморожено до начала прогонов.
2. **`REAL_CASES.md`.** Три публичных случая (Bing Chat, Google Bard, GitHub Copilot) с разбором
   применимости к своему приложению. Вывод - воспроизводить форму Google Bard (файл готовит
   атакующий, файл без проверки становится контекстом модели), потому что канал совпадает буквально:
   импорт истории чата.
3. **`SPEC.md` с гипотезами H1-H4.** До первого живого прогона.
4. **`harness/spec12.py`** - константы: тексты промптов дословно из кода, окно контекста
   (`MAX_CONTEXT_MESSAGES`, `MAX_CONTEXT_CHARS`), тексты защитных блоков всех слоёв, источники
   приёмов сокрытия.
5. **`harness/payloads.py`** - генерация 30 документов (3 вектора x 5 приёмов сокрытия, H4_FAKE_ROLE -
   4 документа на вектор вместо 1-2 у остальных).
6. **`harness/detectors12.py`, `harness/context_window.py`, `harness/input_guard.py`** - пять
   детекторов, честный порт окна контекста (`HistoryMessageMapper.kt`) и настоящего входного гарда
   приложения (`InputGuardMapper.kt`).
7. **`harness/run_indirect.py`** - прогон, `--dry-run`, запись в `raw/run_<timestamp>/`.
8. **Базовая линия (`defense=none`).** Сначала на первой версии набора (`raw/run_20260804_165548`),
   затем набор пересобран после `REAL_CASES.md`, гипотезы H1-H4 проверены заново на новом сырье
   (`raw/run_20260804_171534`).
9. **`harness/control_experiment.py`.** Контрольная демонстрация: один и тот же текст двумя путями -
   через поле ввода (настоящий `input_guard.py`, порт `InputGuardMapper.kt`) и через импорт истории,
   тот же текст, без гарда.
10. **`harness/defenses.py`** - `D1_SANITIZE`, `D2_BOUNDARY`, `D3_OUTPUT` по контракту, плюс
    `D4_PROVENANCE` - добавлен по запросу team-lead, потому что ни один из трёх заданных слоёв не
    отвечает на вопрос "можно ли верить факту из документа".
11. **Гипотезы D-H1 - D-H5 по слоям защиты** - записаны до прогона `--defense sweep`.
12. **`harness/utility_check.py`** - цена защиты D3/D4 на чистых документах без начинки.
13. **`harness/report12.py`** - пересчёт метрик из `raw/` по актуальному детектору, гейт целостности
    замера.
14. **Итоговые документы** - `REPORT.md`, `RESULT.md`, `README.md`, этот `PLAN.md`.

## 4. Развилки и как их закрываем

| Развилка | Решение | Почему |
|---|---|---|
| Где взять три вектора, если в приложении есть только один канал | V1 - настоящий канал (импорт истории чата), V2/V3 - только харнесс, канала в приложении нет | честная оговорка вместо выдуманных путей (веб, почта), которых в приложении не существует |
| Считать ли `H5_MARKDOWN` подтверждённым приёмом | нет, помечен `own_unconfirmed` | источника на markdown-ссылку как **носитель** инъекции не нашли - во всех трёх разобранных случаях картинка или ссылка была каналом **выхода** (эксфильтрация), не входа |
| Нужен ли четвёртый слой защиты | да, `D4_PROVENANCE`, вне контракта | три заданных слоя не защищают от V3 (ложный факт из документа) вообще - D1/D2 чистят текст и роли, D3 сверяет вход/выход, ни один не проверяет достоверность самого утверждения |
| Split dev/holdout | 21/9, у `H4_FAKE_ROLE` - 2 dev + 2 holdout на каждый вектор | тот же принцип, что в task11: защита строится по `dev`, отчёт даётся и по `dev`, и по `holdout`, чтобы разница была видна, а не спрятана |
| Как мерить окно контекста импорта | честный порт `HistoryMessageMapper.kt` (`context_window.py`), один документ-стресс-тест на реальный лимит `MAX_CONTEXT_CHARS=8000` | без этого демонстрация V1 могла провалиться по бытовой причине (инъекция не влезла в окно), а не из-за защиты |

## 5. Что пошло не по плану

- **Пять багов в детекторе, три из них - один и тот же класс** (детектор не покрывает новую
  формулировку, которую выдала модель под давлением нового слоя защиты) - тот же паттерн, что
  в task11.
- **Один баг из пяти был обратным остальным.** Точное совпадение фразы-маркера занижало
  `INJECTED_LINE`/`FALSE_FACT` (модель пересказывала маркер своими словами) - единственный баг
  класса "недосчитал", остальные четыре занижали дырявость завышением ложных срабатываний
  `CONTEXT_POISONED`, либо занижали видимую эффективность защиты (D4).
- **Находка не про баг детектора, а про сам слой защиты.** `D1_SANITIZE` вырезает невидимые символы
  `H2_ZEROWIDTH` и тем самым **собирает** инструкцию обратно в читаемый текст, вместо того чтобы её
  уничтожить - доля успеха по `H2_ZEROWIDTH` не упала, а выросла.
- **CONTEXT_POISONED дважды ловил не то.** Сначала - собственный отказ модели ("я не отвечаю как
  «Dr. AI»" содержит маркер атаки внутри отрицания). После добавления D2+D4 - корректную
  атрибуцию источника ("я нашёл это в тексте, который вы прислали"), что по определению 5.4 -
  ровно противоположность отравлению контекста, а не оно само.

## 6. Открытые концы

- Защита в коде приложения (входной гард на путь импорта, аналог `D1_SANITIZE`) делается параллельно
  другим агентом - числа по ней в этом отчёте не появляются, они отдельная работа.
- `H5_MARKDOWN` не подтверждён источником - собственная вариация, не воспроизведение
  задокументированного случая.
- 3 повтора - минимум контракта, не гарантия. Межсессионный разброс, замеченный в task11 (три
  прогона одной атаки дали три разных числа), на task12 отдельной 10-повторной проверкой не
  перепроверялся - в `REPORT.md` это записано как ограничение, а не скрыто.
