# Контракт: формат весов micro-model

Единственный источник правды для двух реализаций инференса - Python (харнесс замера) и Kotlin (на устройстве).
Обе обязаны давать **одинаковый ответ на одинаковом входе**. Расхождение - дефект, а не «особенность платформы».

Файл весов: `challenge_advanced/task10/results/micro_model.json`
Копия для приложения: `core/micromodel/src/commonMain/composeResources/files/micro_model.json`

Копия обязана быть побайтово равна оригиналу. Расхождение ловится паритет-тестом, но только если его
реально гоняют - поэтому тест обязан падать при отсутствии эталона, а не пропускаться.

---

## 1. Структура JSON

```json
{
  "format_version": 1,
  "trained_on": "task7/data/train_triage_full.jsonl",
  "train_size": 0,
  "seed": 1337,
  "labels": ["EMERGENCY", "DOCTOR_SOON", "SELF_CARE", "OFF_TOPIC"],

  "normalizer": {
    "lowercase": true,
    "yo_to_e": true,
    "collapse_whitespace": true,
    "strip_chars": "...",
    "digit_placeholder": "0"
  },

  "vectorizer": {
    "kind": "tfidf",
    "norm": "l2",
    "analyzers": [
      { "kind": "word", "ngram_min": 1, "ngram_max": 2 },
      { "kind": "char", "ngram_min": 3, "ngram_max": 5 }
    ],
    "vocabulary": {
      "<term>": { "i": 0, "idf": 3.21 }
    }
  },

  "classifier": {
    "kind": "logreg_softmax",
    "bias": [0.0, 0.0, 0.0, 0.0],
    "weights": {
      "<featureIndex>": [0.0, 0.0, 0.0, 0.0]
    }
  },

  "thresholds": {
    "confident_min_prob": 0.0,
    "confident_min_margin": 0.0,
    "always_escalate_labels": ["EMERGENCY"]
  }
}
```

- `labels` - порядок фиксирован. Индекс класса в `bias` и в векторах `weights` соответствует индексу в `labels`.
- `vocabulary` - только те признаки, что пережили обрезку. Ключ - сам терм, `i` - индекс признака, `idf` - готовый вес IDF.
- `weights` - разреженно, ключ это `featureIndex` из `vocabulary[term].i`, значение - вектор длины `labels.length`.
- Признаки, которых нет в `vocabulary`, при инференсе **молча игнорируются**. Это нормальный путь, не ошибка.

**Ограничение размера:** итоговый JSON не больше 500 КБ. Словарь обрезается по важности признака.
Фактический размер и способ обрезки записываются в `SPEC.md`.

---

## 2. Нормализация текста - шаг в шаг

Порядок операций строго такой, менять нельзя:

1. привести к нижнему регистру
2. заменить `ё` -> `е`
3. каждую цифру заменить на `0`
4. каждый символ, не являющийся буквой, цифрой или пробелом, заменить на пробел
5. схлопнуть подряд идущие пробелы в один, обрезать края

Буква определяется как «символ, для которого `Character.isLetter` истинно» (Kotlin) /
`str.isalpha()` для отдельного символа (Python). Это покрывает кириллицу и латиницу одинаково.

---

## 3. Извлечение признаков

**Слова:** нормализованный текст разбивается по пробелу. Униграммы - сами токены.
Биграммы - соседние токены, склеенные через один пробел: `"болит живот"`.

**Символьные n-граммы:** берутся из нормализованного текста, **с пробелами**, окном 3, 4 и 5 символов,
шагом 1. Границы строки не дополняются ничем.

Префиксы термов в словаре, чтобы word и char не смешивались:
- слова: `w:` + терм, например `w:болит`, `w:болит живот`
- символы: `c:` + терм, например `c:бол`

---

## 4. Вектор и предсказание

1. Посчитать частоту каждого терма в документе -> `tf`.
2. Для термов, которые есть в `vocabulary`: `value = tf * idf`.
3. L2-нормализовать вектор: поделить каждое значение на корень из суммы квадратов всех значений.
   Если норма равна нулю - вектор остаётся нулевым.
4. Для каждого класса `k`: `score[k] = bias[k] + sum(value[i] * weights[i][k])`.
5. Softmax со сдвигом на максимум: `p[k] = exp(score[k] - max(score)) / sum(exp(score[j] - max(score)))`.

**Округление:** все вычисления в `double` / `Double`. Расхождение между Python и Kotlin
допускается не больше `1e-6` по каждой вероятности.

---

## 5. Решение об эскалации

```
top1      = класс с максимальной p
top2      = следующий по p
prob      = p[top1]
margin    = p[top1] - p[top2]

status = OK, если prob >= confident_min_prob И margin >= confident_min_margin
         иначе UNSURE

если top1 входит в always_escalate_labels -> статус принудительно UNSURE
```

Последнее правило - осознанная асимметрия: цена пропущенного экстренного случая несопоставима с ценой
лишнего вызова модели, поэтому подозрение на `EMERGENCY` всегда подтверждается большой моделью.

`OK` -> ответ micro-model идёт дальше без вызова LLM.
`UNSURE` -> вызывается большая модель, вердикты сливаются по правилу из раздела 5.1.

---

## 5.1 Слияние вердиктов - только вверх

**Исправлено 2026-07-31 после первого замера. Причина исправления описана ниже, скрывать её нельзя.**

Первая редакция этого документа говорила «вердикт LLM побеждает». Замер показал, что на всех
81 эскалации большая модель ни разу не подняла тяжесть маршрута - 48 раз согласилась, 33 раза понизила.
При таком правиле fallback умеет только облегчать, и каскад теряет экстренные случаи, которые
micro-model нашла верно. Каскад оказался хуже обоих своих уровней по отдельности:
micro 12 из 13 пойманных экстренных, LLM 10 из 13, каскад 9 из 13.

Правило «побеждает LLM» противоречит принципу, зафиксированному ещё в `task7/SPEC.md:8-33`:
цена ошибки несимметрична, при сомнении маршрут поднимается вверх. Исправление возвращает
согласованность спеки, а не подгоняет результат под цифры.

Тяжесть маршрутов, по возрастанию:

```
OFF_TOPIC  <  SELF_CARE  <  DOCTOR_SOON  <  EMERGENCY
```

Правило:

```
final_route = более тяжёлый из (micro_route, llm_route)
```

Большая модель может маршрут **подтвердить или поднять**. Понизить - не может.

Что это значит на практике:
- micro сказала `EMERGENCY`, LLM сказала `DOCTOR_SOON` -> итог `EMERGENCY`
- micro сказала `SELF_CARE`, LLM сказала `EMERGENCY` -> итог `EMERGENCY`
- micro не отработала вообще (битые веса, нет файла) -> итог = вердикт LLM

**Честная оговорка про замер.** Правило исправлено после того, как числа были увидены. Поэтому его
качество на том же наборе кейсов - не доказательство. Исправленный режим меряется отдельным живым
прогоном и в отчёте помечается как «правило изменено после первого замера». Для настоящей проверки
нужен свежий набор кейсов, которого сейчас нет - это записано в ограничениях.

**Почему всё равно применяем в приложении.** Понижение маршрута `EMERGENCY` в продукте про здоровье
детей недопустимо независимо от статистики на 46 кейсах. Это решение по цене ошибки, а не по метрике.

## 5.2 Маршруты вне лестницы тяжести

Добавлено 2026-07-31. У большой модели есть маршруты, которых нет у micro-model и которые не лежат на
шкале медицинской тяжести: `PARENT_SUPPORT`, `DATA_INSIGHT`, `UNKNOWN`. Они про другую ось - эмоциональная
поддержка, работа с цифрами, отказ от классификации.

Соблазн простой: раз тяжести у них нет, слияние их не трогает. **Так делать нельзя.** Тогда появляется
обход правила 5.1 через боковую дверь: micro сказала `EMERGENCY`, большая модель прочитала тревогу
родителя и ответила `PARENT_SUPPORT`, слияние промолчало, экстренный случай потерян.

Правило:

```
если micro_route == EMERGENCY  ->  final_route = EMERGENCY, что бы ни сказала большая модель
иначе если llm_route вне лестницы  ->  final_route = llm_route
иначе  ->  final_route = более тяжёлый из (micro_route, llm_route)
```

То есть жёстко закрывается только `EMERGENCY`. На остальных маршрутах боковая ось разрешена: если micro
сказала `DOCTOR_SOON`, а большая модель считает, что родителю сейчас нужна поддержка - это допустимый
ответ, он никого не убьёт.

`EMERGENCY` - исключение, потому что цена ошибки там несопоставима с ценой лишней тревоги. Ровно та же
логика, по которой `EMERGENCY` от micro-model всегда идёт на подтверждение (раздел 5).

## 5.3 Инвариант весов - проверяется при загрузке

Добавлено 2026-07-31. Правило «`EMERGENCY` всегда идёт на подтверждение» задаётся полем
`thresholds.always_escalate_labels` в JSON, то есть живёт в данных, а не в коде. Это дыра: достаточно
одного кривого переобучения, выпустившего веса без `EMERGENCY` в этом списке, и вся защита отключится
молча. Экстренные случаи пойдут локальным путём, сеть не будет вызвана вообще, и никто этого не заметит.

Поэтому обе реализации при загрузке весов обязаны проверить:

```
labels содержит все четыре маршрута: EMERGENCY, DOCTOR_SOON, SELF_CARE, OFF_TOPIC
thresholds.always_escalate_labels содержит EMERGENCY
```

Если проверка не прошла - **веса считаются негодными целиком**. Micro-model объявляется недоступной,
и всё уходит в большую модель, как будто файла весов нет. Это осознанный fail-safe: лучше потерять
экономию, чем тихо потерять защиту.

Важно: инвариант **не переопределяет** поведение и потому не ломает паритет. Обе реализации либо
принимают одни и те же веса, либо одинаково их отвергают.

Дополнительно харнесс проверяет тот же инвариант **при экспорте**, до записи файла в `results/` -
чтобы негодные веса вообще не появились на диске.

## 6. Паритет - как доказывается

1. Python-харнесс прогоняет весь `cases.jsonl` и пишет в
   `challenge_advanced/task10/results/parity_python.json`:
   для каждого кейса - `id`, `label`, `prob`, `margin`, `status`, и вектор `probs` целиком.
2. Kotlin-тест читает тот же `cases.jsonl` и тот же `micro_model.json`, считает то же самое
   и сверяет с `parity_python.json` с допуском `1e-6`.
3. Тест обязан падать, если хоть один кейс разошёлся.

Без пройденного паритет-теста задача не считается сделанной.
