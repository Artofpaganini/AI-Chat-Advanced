# SPEC - контракт каскада micro-model -> LLM

Замороженный контракт task10. Пороги, правила и гипотезы записаны **до** первого замера.
Задача решения та же, что в task7 и task8 - триаж сообщения родителя. Меняется то, **кто отвечает
первым**.

Формат весов и алгоритм инференса лежат отдельно, в `WEIGHTS_FORMAT.md`. Тот файл - единственный
источник правды для двух реализаций (Python и Kotlin) и здесь не пересказывается.

---

## 1. Зачем дешёвый уровень перед LLM

Из замеров task7 и task8 известно: один вызов `deepseek-v4-flash` на кейс - это примерно 1500 мс и
0.00004 USD. На 50 кейсах это мелочь, на миллионе запросов в месяц - уже нет.

При этом заметная часть входа тривиальна. «Как приучить к горшку» не требует модели за деньги,
чтобы понять, что это `SELF_CARE`. Логистическая регрессия на TF-IDF решает такое за доли
миллисекунды и стоит ноль.

**Главный вопрос замера:** какую долю запросов закрывает дешёвый уровень, и сколько качества за это
платится.

---

## 2. Каскад

```
запрос
  -> [micro-model]  TF-IDF + softmax-регрессия, локально, 0 USD, доли миллисекунды
  -> статус OK      ответ идёт дальше как есть, LLM не зовётся
  -> статус UNSURE  вызов deepseek-v4-flash, его вердикт побеждает
  -> ответ
```

Третьего уровня нет. Ответ большой модели окончательный.

Micro-model отвечает всегда - у неё нет режима отказа. Отказаться она может только через статус
`UNSURE`, и тогда решение принимает LLM.

## 3. Micro-model

| Что | Как |
|---|---|
| Признаки | TF-IDF: слова 1-2 граммы плюс символьные 3-5 граммы |
| Классификатор | мультиклассовая логистическая регрессия (softmax) на 4 класса |
| Обучение | полный batch, градиентный спуск с моментом, L2-регуляризация |
| Библиотеки | **только стандартная библиотека Python 3.9** |
| Классы | `EMERGENCY` / `DOCTOR_SOON` / `SELF_CARE` / `OFF_TOPIC` |
| Корпус | `../task7/data/train_triage_full.jsonl`, 1019 примеров |

Ни numpy, ни sklearn в системе нет, ставить пакеты запрещено. Матан написан руками. Это не поза, а
условие задачи: та же арифметика повторяется на Kotlin, где sklearn всё равно не будет.

Символьные n-граммы взяты не для красоты. Вход - живой родительский текст с опечатками, капсом и
обрывками слов. Словарь из целых слов на таком входе рассыпается, символьные куски держатся лучше.

### Обрезка словаря

Полный словарь символьных 3-5 грамм на 1019 текстах - это десятки тысяч признаков, в 500 КБ они не
влезут. Режем в два прохода:

1. отбрасываем термы, встретившиеся меньше чем в `MIN_DF` документах,
2. обучаемся, считаем важность признака и оставляем верхушку.

Важность признака `i`:

```
importance(i) = (max_k w[i][k] - min_k w[i][k]) * sqrt(df(i) / N)
```

Первый множитель - разброс весов между классами. Признак с одинаковым весом на всех четырёх классах
после softmax не решает ничего, каким бы большим этот вес ни был. Второй множитель - поправка на
охват: терм, который встретился в двух документах, не должен вытеснять терм из двухсот.

После обрезки веса **обучаются заново** на урезанном словаре. Иначе L2-норма вектора поедет
(нормировка идёт по тем термам, что есть в словаре) и паритет с Kotlin сломается на ровном месте.

Фактический размер файла и число признаков записываются в `REPORT.md` по факту.

## 4. Подбор порогов

`confident_min_prob` и `confident_min_margin` подбираются **только на обучающем корпусе**.
`cases.jsonl` в подборе не участвует ни на одном шаге - иначе это подгонка под ответ, а не замер.

Процедура:

1. Корпус делится 80/20 со стратификацией по классу, seed 1337.
2. На 80% обучается модель, включая обрезку словаря.
3. На 20% перебирается сетка: `prob` из `0.50 0.60 0.70 0.80 0.90`, `margin` из
   `0.00 0.10 0.20 0.30 0.40`. Всего 25 пар.
4. Для каждой пары применяется правило из раздела 5 контракта, вместе с принудительной эскалацией
   `EMERGENCY`. Считается два числа: `coverage` - доля кейсов со статусом `OK`, и `precision_on_ok` -
   точность на этой доле.
5. Берётся пара с максимальным `coverage` при `precision_on_ok >= 0.95`. Если ни одна пара порога не
   держит, берётся пара с максимальной `precision_on_ok`.
6. Финальные веса обучаются заново на всех 1019 примерах. Пороги переносятся из шага 5 без изменений.

Смысл критерия простой. Покрытие - это экономия, точность на покрытии - это цена экономии.
Мы фиксируем цену и максимизируем экономию, а не наоборот.

**Известное ограничение:** финальная модель обучена на большем количестве данных, чем та, на которой
подбирались пороги, и потому увереннее. Порог, откалиброванный на срезе, на финальной модели даст
чуть большее покрытие, чем ожидалось. Считаем это меньшим злом, чем пороги из воздуха.

## 5. Асимметрия по EMERGENCY

Контракт, раздел 5: если micro-model назвала `EMERGENCY`, статус принудительно становится `UNSURE` и
кейс уходит наверх, какой бы высокой ни была вероятность.

Это осознанная трата. Цена пропущенного экстренного случая - здоровье ребёнка. Цена лишнего вызова -
0.00004 USD. Сравнивать тут нечего.

Обратный случай - micro-model назвала не `EMERGENCY`, а на деле экстренный - правилом не
закрывается. Его ловит только общий порог уверенности. Это дыра, и её размер надо измерить, а не
заклеить словами. Метрика `missed_emergency` в режиме `only_micro` показывает её честно.

## 6. Режимы, которые сравниваем

| Режим | Что делает | Вызовов LLM на 50 кейсов |
|---|---|---|
| `only_llm` | всё уходит в `deepseek-v4-flash` | 50 |
| `only_micro` | только micro-model, эскалации нет вообще | 0 |
| `cascade` | micro-model, эскалация по `UNSURE` | сколько получится |

`only_llm` и `only_micro` - не стратегии, а границы. Верхняя граница по качеству и цене, нижняя по
цене и качеству. Без них цифры каскада не с чем сравнивать.

## 7. Что меряем

| Метрика | Смысл |
|---|---|
| `handled_by_micro` | сколько запросов micro-model закрыла сама |
| `fallback_count` | сколько ушло наверх |
| `llm_calls` | общее число вызовов большой модели |
| `accuracy` | доля совпадений с золотым маршрутом |
| `missed_emergency` | пропущенные экстренные случаи. **Блокирующая метрика, цель - ноль** |
| `false_emergency` | ложные тревоги, цена безопасности |
| `cost_usd` | суммарная стоимость. Вызовы micro-model стоят 0 |
| `latency_mean`, `latency_p50`, `latency_p95` | по полному циклу, включая оба уровня при эскалации |
| `micro_latency_ms` | отдельно время самой micro-model |
| по группам | `clean` / `borderline` / `noisy` - разбивка точности |

Кейсы с `expected_status = FAIL` (пустой ввод, мусор) из подсчёта точности исключаются - так же, как
в task7, task8 и task9. Их 4 из 50, остаётся 46 оцениваемых.

## 8. Правила замера

- Набор тот же: `../task7/data/cases.jsonl`, 50 кейсов, три группы сложности.
- Каждый режим прогоняется **три раза**. Решение принимается по худшему прогону, а не по среднему.
  Урок task8: облачная модель на одном и том же входе даёт разные ответы, одиночный замер обманывает.
- `only_micro` детерминирован, три его прогона обязаны совпасть до последнего знака. Если не
  совпали - это дефект харнесса, и он ловится тем же способом, что и разброс облака.
- Seed 1337 везде, где есть случайность: разбиение корпуса, порядок обхода.
- Ключ только из окружения или `local.properties`. В `raw/`, `results/` и markdown не попадает
  никогда, ни в каком виде.
- Все числа в `REPORT.md` пересчитываются из `raw/` скриптом `report10.py`. По памяти - ни одного.

## 9. Гипотезы

Записаны заранее, чтобы потом не подгонять объяснение под результат. Каждая проверяется числом.

1. **Micro-model заметно слабее LLM на пограничных случаях.** TF-IDF ловит лексику, а не смысл, а
   группа `borderline` построена так, что решает именно смысл. Ожидаем разрыв не меньше 15 пунктов
   точности на группе `borderline` между `only_micro` и `only_llm`.

2. **Каскад срезает не меньше 40% вызовов LLM.** Из 50 кейсов 13 золотых `EMERGENCY`, к ним добавятся
   ложные срабатывания и неуверенные - но большая часть `SELF_CARE` и `OFF_TOPIC` должна закрыться
   внизу. Ожидаем `llm_calls` каскада не больше 30 из 50.

3. **Каскад не теряет ни одного экстренного случая относительно `only_llm`.** Правило принудительной
   эскалации `EMERGENCY` работает только в одну сторону, поэтому гипотеза нетривиальна: потерять
   можно на тех кейсах, где micro-model уверенно назвала не-`EMERGENCY`. Ожидаем
   `missed_emergency` каскада равным `missed_emergency` у `only_llm`.

4. **Micro-model быстрее облачного вызова минимум в 1000 раз.** Ожидаем медиану времени
   micro-model ниже 2 мс против примерно 1500 мс у облака, и падение средней задержки каскада
   пропорционально доле, закрытой внизу.

5. **Пересечения между обучающим корпусом и `cases.jsonl` нет.** Наборы делались раздельно.
   Ожидаем ноль точных совпадений нормализованного текста и ноль пар с близостью Жаккара выше 0.9.

6. **Micro-model проседает на шумной группе сильнее, чем на чистой.** Капс, опечатки и обрывки
   ломают словарные признаки. Ожидаем точность на `noisy` ниже, чем на `clean`, не меньше чем на
   10 пунктов.

Если гипотеза не подтвердится - записываем как есть. Отрицательный результат публикуется без правки
формулировки.

## 11. Правка контракта по ходу задачи

**Дата: 2026-07-31, после первого замера.**

Гипотезы из раздела 9 и условия гейта из раздела 10 не менялись и не будут меняться. Этот раздел
дописан отдельно, чтобы правка была видна, а не растворилась в тексте.

### Что изменено

`WEIGHTS_FORMAT.md`, добавлен раздел 5.1 «Слияние вердиктов - только вверх».

Было: при эскалации **вердикт LLM побеждает**.
Стало: `final_route = более тяжёлый из (micro_route, llm_route)` по шкале
`OFF_TOPIC < SELF_CARE < DOCTOR_SOON < EMERGENCY`. Большая модель может маршрут подтвердить или
поднять, понизить - не может.

### Почему изменено

Первый замер показал: за 81 эскалацию большая модель ни разу не подняла тяжесть маршрута -
48 согласий, 33 понижения, 0 повышений. При правиле «побеждает LLM» fallback умеет только облегчать,
и через него ушли три верно найденных `EMERGENCY` (`borderline_06`, `borderline_08`,
`borderline_11`). Каскад оказался хуже обоих своих уровней: micro 12 экстренных из 13, LLM 10 из 13,
каскад 9 из 13.

Прежнее правило противоречило принципу из `task7/SPEC.md:8-33` - цена ошибки несимметрична, при
сомнении маршрут поднимается вверх. Правка возвращает согласованность спеки, а не подгоняет
результат под цифры.

### Как это меряется

Добавлен четвёртый режим `cascade_max`. Он прогнан **живьём, три повтора**, сырьё в
`raw/pipeline_cascade_max*.jsonl`. Это не пересчёт старого сырья: постфактум-блок `posthoc` в
`results/pipeline_report.json` остаётся на месте как был и живыми числами не заменяется.

Условия гейта не менялись. Те же пять пунктов применяются к `cascade_max` справочно, код возврата
по-прежнему определяет режим `cascade` - именно он был предметом первого замера.

### Оговорка, без которой правка не считается честной

Правило изменено **после** того, как числа были увидены. Значит его поведение на этом же наборе
доказательством не является: набор уже потрачен на постановку диагноза. Для настоящей проверки нужен
свежий набор кейсов, которого сейчас нет. Это записано в ограничениях `REPORT.md`.

В приложение правило всё равно берётся - по цене ошибки, а не по метрике. Понижение маршрута
`EMERGENCY` в продукте про здоровье детей недопустимо независимо от статистики на 46 кейсах.

### Правка третья: инвариант весов

**Дата: 2026-07-31.**

`WEIGHTS_FORMAT.md`, добавлен раздел 5.3 «Инвариант весов - проверяется при загрузке».

**Что за дыра.** Правило «`EMERGENCY` всегда идёт на подтверждение» задаётся полем
`thresholds.always_escalate_labels` в JSON, то есть живёт в данных, а не в коде. Один кривой retrain,
выпустивший веса без `EMERGENCY` в этом списке, отключает защиту молча. Экстренные пойдут локальным
путём, сеть не будет вызвана вообще, и в метриках это будет выглядеть как выросшая экономия.

**Что проверяется.** При загрузке весов и отдельно при экспорте, до записи файла:

```
labels содержит все четыре маршрута: EMERGENCY, DOCTOR_SOON, SELF_CARE, OFF_TOPIC
thresholds.always_escalate_labels содержит EMERGENCY
```

Не прошло - веса негодны целиком. Micro-model объявляется недоступной, весь трафик идёт в большую
модель, как будто файла весов нет. Осознанный fail-safe: потерять экономию дешевле, чем потерять
защиту.

**Где в коде.** Загрузка - `harness/micro_model.py:232` (`check_invariant`), вызывается из
`from_json_document` и из `save_model`. Экспорт - `harness/train_micro.py:545`, до `save_model`,
с кодом возврата 3 при провале. `run_pipeline.py` и `report10.py` ловят `InvalidWeightsError` и
сообщают внятно вместо трейсбека.

**Почему это не ломает паритет.** Инвариант ничего не переопределяет: код не подставляет `EMERGENCY`
в список сам и не меняет поведение модели. Он только отказывается работать с весами, не
соответствующими контракту. Обе реализации либо принимают одни и те же веса, либо одинаково их
отвергают.

**Модель не переобучалась.** Текущий `results/micro_model.json` инвариант проходит: `labels` содержит
все четыре маршрута, `always_escalate_labels` равен `["EMERGENCY"]`. Файл не тронут, паритет-тест с
Kotlin пересдавать не нужно.
