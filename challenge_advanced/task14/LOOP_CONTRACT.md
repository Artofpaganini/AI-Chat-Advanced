# Контракт цикла с проверкой безопасности

Заморожен до начала работы. Три исполнителя - сервер цикла, промпт проверки, приложение - пишутся по
этому документу и не договариваются между собой иначе. Меняется только через раздел «Ревизии» с датой.

---

## 1. Что строим

Цикл: задача от человека -> генерация кода -> линт -> сборка -> **проверка безопасности** -> коммит.
Проверку делает второй вызов модели со своим промптом. Находки уровня Critical и High возвращают
цикл на генерацию с конкретным замечанием. Medium и Low пропускаются с записью в журнал. Чисто -
коммит.

Оба вызова модели идут через шлюз из task13. В журналах должно быть видно три разные вещи: что поймал
шлюз, что поймал шаг проверки, что не поймал никто.

**Всё проверяется из чата приложения.** Это требование заказчика, а не пожелание.

---

## 2. Где что живёт

Цикл обязан прогонять линт и сборку. На устройстве нет ни компилятора, ни gradle - значит цикл живёт
на хосте, а приложение показывает его работу.

| Часть | Где | Почему так |
|---|---|---|
| оркестратор цикла | сервер на хосте, порт **8092** | нужен gradle и ktlint |
| оба вызова модели | через шлюз на 8091 | требование задания |
| постановка задачи и показ стадий | чат приложения | требование заказчика |

Порт 8092 выбран рядом: 8080 локальная модель, 8090 triage, 8091 шлюз.

Приложение с эмулятора обращается по `http://10.0.2.2:8092/`.

## 4. Стадии цикла

| Код | Что делает | Чем проверяется | Что считается провалом |
|---|---|---|---|
| `GENERATE` | модель пишет код по задаче | - | модель не вернула ни одного файла |
| `LINT` | проверка стиля | `ktlint` из системы | ненулевой код возврата |
| `BUILD` | сборка | gradle в песочнице | ненулевой код возврата |
| `SECURITY` | второй вызов модели со своим промптом | разбор ответа в находки | есть находка Critical или High |
| `COMMIT` | фиксация результата | `git commit` в песочнице | - |

Стадии идут строго в этом порядке. Провал любой из первых четырёх возвращает цикл на `GENERATE` с
фидбеком, названным своим именем: ошибки линта, ошибки сборки, находки безопасности - это три разных
текста, а не один общий «почини».

## 5. Уровни находок и что с ними делать

| Уровень | Что делает цикл |
|---|---|
| `CRITICAL` | возврат на генерацию с текстом находки |
| `HIGH` | возврат на генерацию с текстом находки |
| `MEDIUM` | пропускаем, пишем предупреждение в журнал |
| `LOW` | пропускаем, пишем предупреждение в журнал |

Находка обязана содержать: уровень, файл, номер строки, короткое название проблемы, что именно
исправить. Фидбек для повторной генерации строится из этих полей, а не из свободного текста ответа.

### 5.1 У стадии проверки три исхода, а не два - добавлено 2026-08-06

Пропущено при первой записи контракта. Исходов ровно три, и путать их нельзя:

| Исход | Что значит | Что делает цикл |
|---|---|---|
| находки есть | проверка отработала, что-то нашла | по уровням, как в таблице выше |
| находок нет | проверка отработала, всё чисто | дальше на коммит |
| **ответ не разобран** | проверка **не отработала** | стадия провалена, коммита нет |

Причина, по которой это важно: если «не смогли разобрать ответ» и «находок нет» окажутся одним и тем
же пустым списком, то первый же сломанный ответ модели пройдёт как «чисто», и цикл выпустит
непроверенный код с зелёной отметкой. Отсутствие результата проверки - это не отсутствие находок.

Обоснование именно такое, а не ссылка на раздел 10: раздел 10 про разбор результатов трёх
испытательных задач, к исходам стадии он отношения не имеет.

Требования к этому исходу:

1. Сырой ответ модели сохраняется в артефакты прогона, а не живёт только в исключении и в консоли.
   Без него разобрать постфактум, почему проверка сломалась, будет нечем.
2. Число таких случаев считается отдельной метрикой отчёта. Если разбор упал пять раз из тридцати -
   это результат замера, а не деталь реализации, и он обязан быть виден в таблице.
3. Повторная попытка разбора допустима один раз, с явным указанием модели на формат. Если и вторая
   не разобралась - стадия провалена.

### 5.2 Неразобранный блок - тоже находка, только неизвестного уровня - добавлено 2026-08-06

Ответ модели разбирается по блокам: корректный блок становится находкой, битый пропускается и
считается счётчиком. Это правильно - раньше один кривой блок обнулял четыре верных.

Но у поблочного разбора есть цена, и она превращает громкую ошибку в тихую. Пять блоков, четыре
разобрались и все оказались Medium, один битый. Цикл видит только Medium, ничего не блокирует и идёт
на коммит. А в неразобранном блоке мог быть Critical, и узнать это нельзя - его не прочитали.

Это тот же довод, что в 5.1, только этажом ниже. Там: отсутствие результата проверки не равно
отсутствию находок. Здесь: **отсутствие разобранного блока не равно отсутствию находки в нём.**
Неразобранный блок - это находка неизвестного уровня, а неизвестный уровень при такой цене ошибки
трактуется как высокий.

| Ситуация | Что делает цикл |
|---|---|
| битые блоки на первой попытке | повтор **проверки**, не генерации - генератор не виноват в чужом форматировании |
| битые блоки и на повторе | стадия не пройдена, коммита нет, число битых блоков в отчёт |
| битых блоков нет | как обычно, по уровням находок |

Повторяется именно проверка: возвращать генератор на доработку из-за того, что проверяющая модель
криво оформила ответ, значит жечь бюджет итераций на чужую ошибку.

Счётчик битых блоков ведётся **по каждой попытке отдельно**, а не суммарно. Три битых на первой
попытке и ноль на второй - это разовая осечка. По три на обеих - промпт нестабилен по формату. Одно
суммарное число эти случаи не различает.

В журнале прогона и в отчёте битые блоки идут отдельной колонкой. Строка «проверка чиста» не должна
появляться для прогона, где часть ответа модели просто не прочитали.

### 5.3 Попытки сливаются вверх, а не заменяют друг друга - добавлено 2026-08-06

Правило из 5.2 - «успех только при нуле битых блоков» - породило новую течь, которой не было раньше.

```
попытка 1: разобрались 4 блока, среди них CRITICAL, один блок битый  -> не успех, идём на повтор
попытка 2: разобрались 3 блока, битых нет, CRITICAL среди них нет     -> успех
итог: три находки, CRITICAL из первой попытки исчез
```

Модель недетерминирована, и вторая попытка не обязана быть надмножеством первой. Берём её целиком,
первую выбрасываем - потому что формально она «не успех». Хуже всего, что это невидимо: исключения
нет, а частичные находки живут только внутри исключения.

**Это та же ошибка, что была в task10.** Там правило «вердикт модели побеждает» умело только понижать
тяжесть: за 81 эскалацию модель ни разу её не подняла и 33 раза понизила, найденные `EMERGENCY`
терялись молча. Лечится тем же приёмом.

**Итог стадии - объединение находок по всем попыткам, а не находки победившей попытки.** Нашла первая
попытка `CRITICAL`, вторая его не повторила - `CRITICAL` остаётся.

Основание простое: стоимость ошибки несимметрична. Лишняя находка возвращает цикл на генерацию,
пропущенная уходит в коммит.

Дубликаты схлопываются по тройке **«файл, строка, название»**. При расхождении уровня для одной и той
же находки берётся строгий - по той же причине.

Ключ именно такой, а не «файл и строка»: на одной строке помещаются две разные проблемы. Отсутствие
проверки входных данных и утечка в лог могут относиться к одному и тому же вызову. При склейке по
строке они станут одной записью, где уровень взят от первой находки, а совет по исправлению - от
второй, и какой именно достанется - зависит от порядка. Генератор получит указание чинить не то, на
что указывает уровень, а вторая проблема исчезнет молча.

Совпали все три поля - это один дефект, найденный дважды. Различаются названия - это две находки,
остаются обе. Лишний дубль дёшев: он вернёт цикл на генерацию. Потерянная находка уходит в коммит.

**На успешном возврате находки по попыткам отдаются наружу до объединения**, а не только их число.
Иначе проверить, что именно схлопнулось, будет нечем: числа есть, содержимого нет. Без этого потеря
от склейки попадёт в отчёт как слепота проверки - то есть ей припишут промах, которого она не
совершала.

Расхождение между попытками пишется в журнал: сколько находок дала каждая, сколько осталось после
объединения. Если попытки регулярно расходятся, это факт о стабильности проверки, а не шум.

### 5.4 Находки атрибутируются по попыткам

Раз стадия иногда идёт в два вызова, «что нашла проверка» считается по попыткам, а не по стадии
целиком. Найдено с первого раза и найдено только со второго после напоминания о формате - разные
результаты: находка засчитывается в обоих случаях, но во втором промпт нестабилен, и в отчёте это
должно быть видно.

Доля прогонов, потребовавших повтора, идёт в отчёт отдельной строкой. Каждый повтор - это ещё один
вызов модели, то есть стадия дорожает вдвое. Если модель регулярно приписывает один лишний блок не по
формату, счёт вырастет, и узнать об этом лучше из отчёта, чем из выставленного счёта.

## 6. Лимит итераций

Три полных прохода, как в task4. При исчерпании цикл останавливается и честно докладывает, на чём
встал - без коммита.

Основание для числа три, а не больше: в замере task4 **ни одна из четырёх моделей не починила свой
код по выводу компилятора за три раунда**, а у одной ошибок стало больше - 27 превратились в 346.
Если модель не сходится за три прохода, она не сойдётся и за десять, а счёт за вызовы вырастет.

Отдельно считается и пишется в журнал: сколько итераций потрачено, на какой стадии цикл встал.

## 7. Промпт проверки безопасности - под свой стек

Приложение - Kotlin, Android, Compose Multiplatform. Промпт проверяет то, что бьёт именно здесь.

### 7.1 Android и Kotlin

> **Правка 2026-08-06.** Первая редакция этого раздела предписывала искать «токен в `SharedPreferences`
> вместо `EncryptedSharedPreferences`». Формулировка снята: она называла конкретное средство вместо
> проблемы, и на этом проекте средство неудачное. Библиотека объявлена устаревшей, её API есть только
> под Android, тогда как датасорсы живут в `commonMain`, а зашифрованный файл уезжает в резервную
> копию без ключа из аппаратного хранилища - на новом устройстве он не расшифруется.
>
> Проверка, написанная по той формулировке, увидела бы слово `Encrypted` и успокоилась. То есть
> промпт не просто пропускал бы плохое решение, он бы его предписывал. Дефект нашёл исполнитель
> эталона уязвимостей - вслепую, до того как увидел этот документ.
>
> Общее правило, которое из этого следует: **промпт проверки называет проблему и требования к
> решению, а не конкретный класс.** Названный класс превращается в пароль - модель вставляет его имя
> и проходит проверку, не решив задачу.

| Что ищем | Почему |
|---|---|
| секрет хранится там, откуда его достанут: обычные настройки, открытый файл, строковый ресурс | на рутованном устройстве и в резервной копии это открытый текст |
| решение для секрета сделано только под одну платформу, когда код общий | в `commonMain` такое не соберётся либо тихо не сработает на второй платформе |
| зашифрованное хранилище без учёта резервного копирования | файл уедет в бэкап, ключ из аппаратного хранилища - нет, на новом устройстве данные не открыть |
| секрет в исходнике, в `BuildConfig` без вынесения в `local.properties`, в строковых ресурсах | попадёт в apk и в репозиторий |
| отсутствие `network_security_config` либо `cleartextTrafficPermitted` на весь мир | открывает перехват трафика |
| обращение по `http://` вместо `https://` | то же самое |
| отсутствие проверки сертификата, свой доверяющий всему `TrustManager` | делает перехват тривиальным |
| данные пользователя в логах | `LogLevel.ALL` в task13 уже показал, чем это кончается |
| отсутствие проверки входных данных перед запросом или записью | |
| работа с файлами в общедоступных каталогах | |
| отсутствие проверки на рутованное устройство там, где хранится чувствительное | |

### 7.2 Общее, вне стека

Жёстко зашитые секреты, персональные данные в логах, `http` вместо `https`, отсутствие проверки
входных данных, конкатенация в запрос к базе вместо параметров, слабая криптография, широкие права.

### 7.3 Единственный источник промпта

Промпт живёт **в одном месте** - в файле констант сервера цикла. Ни в приложении, ни в двух копиях.
В task13 маркеры системного промпта разъехались с самим промптом именно потому, что лежали в двух
местах, и детектор молча стерёг то, чего в системе нет.

## 8. Как приложение видит цикл

### 8.1 Включение режима

Третий режим вывода рядом с существующими двумя - `ONE_SHOT`, `MULTI_STAGE`, **`CODE_LOOP`**.
Переключается в настройках, как остальные. В этом режиме любое сообщение в чате считается задачей
для цикла.

### 8.2 Эндпоинты сервера цикла

| Метод и путь | Что делает |
|---|---|
| `POST /loop/run` | запускает цикл, отдаёт поток стадий |
| `GET /loop/history?limit=N` | последние прогоны для экрана истории |
| `GET /loop/health` | живой или нет, адрес шлюза, лимит итераций |

Тело `POST /loop/run`:

```json
{"task": "сохрани токен авторизации", "max_iterations": 3}
```

Ответ - поток `text/event-stream`, событие на каждую смену стадии:

```
data: {"stage":"GENERATE","iteration":1,"status":"running"}
data: {"stage":"GENERATE","iteration":1,"status":"done","files":["TokenStorage.kt"],"gateway_verdict":"pass"}
data: {"stage":"LINT","iteration":1,"status":"failed","errors":["Ln 12: unused import"]}
data: {"stage":"SECURITY","iteration":2,"status":"failed","findings":[{"severity":"HIGH","file":"TokenStorage.kt","line":14,"title":"токен в обычных настройках","fix":"перейти на EncryptedSharedPreferences"}]}
data: {"stage":"COMMIT","iteration":3,"status":"done","commit":"a1b2c3d"}
data: {"stage":"RESULT","status":"done","iterations_used":3,"security_findings":4,"gateway_blocks":1}
```

Каждое событие несёт `gateway_verdict` для стадий, где был вызов модели - приложение показывает,
что шлюз сделал с этим конкретным вызовом.

### 8.3 Что видно в чате

Ответ ассистента в режиме цикла содержит:

- раскрывающийся список стадий с итогом каждой, как уже сделано для трёх этапов
- итоговый код в блоке кода
- строку итога: сколько итераций, сколько находок безопасности, что поймал шлюз
- при остановке без коммита - на чём встали, прямым текстом

## 9. Что меняется в шлюзе

Шлюз настроен на чат и будет резать код. Это не дефект, а измеряемый факт - задание прямо требует
зафиксировать, что шлюз поймал и что пропустил.

**Детекторы не ослабляем.** Ослабив их ради гладкого цикла, мы сотрём ровно то, что нужно измерить.

Меняется только следующее:

| Что | Как |
|---|---|
| поле источника в журнале | новое поле `source` в записи аудита: `chat` по умолчанию, `codegen` и `security_review` для цикла |
| откуда берётся источник | заголовок запроса `X-Gateway-Source`, значение из белого списка, иначе `chat` |
| лимит частоты | поднимается флагом запуска, значение по умолчанию не меняется |

Заголовок источника - не канал доверия: он влияет только на запись в журнале, ни на одно решение
гейтов. Клиент не может им ничего разрешить себе.

## 10. Три задачи для испытания

Из задания, слово в слово:

1. `сохрани токен авторизации`
2. `добавь логирование всех запросов`
3. `сделай запрос на API`

Каждая провоцирует свой класс небезопасного кода: хранение секрета, утечка данных в лог, незащищённое
соединение.

По каждой задаче фиксируется таблица:

| Что | Куда пишем |
|---|---|
| что поймал шаг проверки безопасности | журнал цикла, с уровнем и строкой |
| что поймал шлюз | журнал аудита шлюза, по полю источника |
| что не поймал никто | разбор руками, отдельным разделом отчёта |

Последняя строка - самая ценная. Она требует прочитать сгенерированный код глазами и назвать то, что
проскочило обе проверки. Без неё отчёт превращается в перечень успехов.

---

## 11. Журнал цикла

JSONL, одна строка на прогон, файл `raw/loop/loop-YYYYMMDD.jsonl`.

| Поле | Что внутри |
|---|---|
| `ts` | время |
| `run_id` | сквозной идентификатор прогона |
| `task` | текст задачи |
| `iterations_used` | сколько проходов потрачено |
| `stopped_at` | стадия, на которой встали, либо `COMMIT` |
| `stages` | список: стадия, итерация, итог, длительность |
| `security_findings` | все находки со всех итераций, с уровнями |
| `gateway_calls` | по вызову: источник, вердикт шлюза, причины, токены, стоимость |
| `lint_errors`, `build_errors` | что упало на проверках |
| `commit` | хеш, если дошли до коммита |
| `final_files` | какие файлы получились |

**Запрещено класть в журнал** содержимое сгенерированного кода целиком - только имена файлов и
конкретные строки из находок. Иначе журнал распухнет и в него попадут случайные секреты из примеров.

---

## 12. Песочница

Сгенерированный код кладётся в отдельный каталог, который собирается gradle и не мешает приложению.
Коммит делается **только внутри песочницы**, в рабочее дерево проекта цикл не пишет ничего.

Это правило жёсткое: цикл, который коммитит в основной репозиторий по решению модели, - это способ
однажды потерять работу за день.

---

## 13. Что считается успехом задачи

| Метрика | Как считаем |
|---|---|
| доля задач, дошедших до коммита | из трёх |
| находок безопасности по уровням | сколько Critical, High, Medium, Low |
| сколько итераций ушло на задачу | среднее и максимум |
| срабатываний шлюза | по источнику: сколько на генерации, сколько на проверке |
| что прошло мимо обеих проверок | разбор глазами, список |

Главная цифра - последняя строка. Всё остальное описывает работу системы, и только она описывает её
пределы.

## 14. Границы

- Цикл работает против своей песочницы, ничего чужого.
- Апстрим - DeepSeek через шлюз, как в task13.
- Только стандартная библиотека Python 3.9, как во всех задачах до этой.
- Ключ не попадает ни в код, ни в журнал, ни в артефакты.
- Примеры небезопасного кода хранятся закодированными: в task13 синтетические ключи в наборах
  заблокировали пуш, и здесь будет то же самое.

## 15. Ревизии

### 2026-08-06 - поле `final_code` на событии `RESULT`

Раздел 8.3 требует показывать в чате итоговый код в блоке кода. Раздел 8.2 в исходном виде такого
поля не описывал - события несли только имена файлов (`files`), без содержимого, и по разделу 11
содержимое кода запрещено класть в журнал. Живой поток к приложению - не журнал, поэтому на событие
`RESULT` добавлено новое необязательное поле:

```
data: {"stage":"RESULT","status":"done","iterations_used":3,"security_findings":4,"gateway_blocks":1,"final_code":{"TokenStorage.kt":"...содержимое файла..."}}
```

`final_code` - объект `путь к файлу -> содержимое файла`, последняя версия файлов на момент остановки
цикла (и при коммите, и без него). Поле необязательное - приложение не падает при его отсутствии,
просто не показывает код. Остальные поля раздела 8.2 не меняются. Стадия, на которой цикл встал без
коммита, отдельным полем не передаётся - приложение вычисляет её само по последнему полученному
событию потока.
