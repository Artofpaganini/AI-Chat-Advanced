# Задача 3 - Тестирование в два уровня

## Что делали

Взяли приложение Jarvis (KMM + Compose Multiplatform, чат с DeepSeek) и закрыли его тестами на двух уровнях. Первый уровень - обычные код-тесты: агент сам прошёлся по модулям, нашёл непокрытую бизнес-логику (мапперы, репозитории, use-case, датасорсы, базовая ViewModel), написал тесты и прогнал их гредлом. Второй уровень - smoke по живому UI: описали пользовательские сценарии простым текстом, и агент сам протыкивал приложение через MCP-драйверы - claude-in-mobile на Android-эмуляторе и Playwright на web-сборке, со скриншотом на каждом шаге и вердиктом PASS/FAIL. Отдельно сделали профиль `pr-check`, который после PR запускает оба уровня и собирает один общий отчёт с вердиктом MERGE-READY или BLOCKED.

## Что получилось, а что нет

Получилось:

- 78 код-тестов зелёные с первого прогона, 0 падений. Было 30, добавили 48.
- Покрыты 3 модуля вместо требуемых 3+: `feature/chat`, `feature/ai`, `core/viewmodel`.
- Все 5 сценариев описаны так, что их правит непрограммист - обычным текстом, без кода.
- Финальный smoke прогнан на двух таргетах сразу, 8/8 PASS, ни одного FATAL за прогон.
- Ответы DeepSeek в прогоне живые, а не моки, и на двух таргетах они разные - это доказывает, что были два независимых вызова, а не пересказ одной записи.
- Export проверялся не по тосту, а по факту: файл на устройстве 988 байт, ключ localStorage на web 1010 байт.
- Persistence проверялся честно: после `app:stop` `pidof` пустой, процесс убит по-настоящему, после запуска новый PID (9127 вместо 4889) и 8 сообщений с диска.
- Найдены 2 реальных дефекта приложения, оба на web.
- Flow-интеграция описана профилем, а не на словах: есть стадии, обязанности, запреты и формат отчёта.

Не получилось или сделано частично:

- `claude-in-chrome` не завёлся ни разу. За три с лишним рестарта сессии расширение не подключилось к MCP-серверу. Ноль полезных прогонов, из документации убран.
- Модуль `browser` у claude-in-mobile для web не годится. В нём жёстко зашит `--disable-gpu`, Skiko молча получает null-контекст, и Compose просто не рисует canvas. Обёртка через `CHROME_PATH` вернула настоящий GPU, но canvas всё равно не появился - копать дальше в чужой инструмент не стали, взяли Playwright.
- Из-за этого первый заход на web дал 0 из 5: все пять сценариев в `smoke/web/report.md` стоят как «не прогнан».
- Кириллица на Android не вводится - `adb input text` не умеет не-ASCII и падает с `NullPointerException`. Часть прогона шла латиницей.
- Была ошибка измерения на стороне тестировщика: проверяли `document.querySelector('canvas')`, а Compose кладёт canvas в shadow DOM, где селектор не найдёт его никогда. Вывод «после починки GPU всё ещё сломано» был сделан по неверному индикатору.
- Сценарий 3 (избранное + фильтр) отдельным прогоном в финальном заходе не считается - его проверки встроены в сценарии 2 и 5. Поэтому итог 8 прогонов, а не 10.
- Чтобы написать тесты, пришлось трогать прод: подключить `ktor-client-mock`, сделать `AiRepository` публичным и снять `internal` с конструктора `SendMessageUseCase`, включить `withHostTest {}` в `core/viewmodel`. Первые два - прямое следствие того, что `ChatViewModel` был не тестируем без ослабления видимости.
- `README.md` и `pr-check-report.md` остались на старых цифрах - 30 тестов, 5 файлов, smoke через adb. Актуальные цифры только в `FINAL_REPORT.md`. Две версии правды в одной папке.
- Чек-лист приёмки в `PLAN.md` (раздел 5) остался с непроставленными галочками, хотя по `FINAL_REPORT.md` все четыре пункта закрыты.
- В авто-раннере `run_smoke.sh` два сценария из пяти не дают машинного вердикта, только `manual-check`.

## Что это даёт дальше

1. Регрессию ловим до мержа, а не после. Профиль `pr-check` прогоняет оба уровня и выдаёт один вердикт - MERGE-READY или BLOCKED. Мержить на красном профиль прямо запрещает.
2. Smoke-сценарии пишет и правит кто угодно, включая менеджера или тестировщика без кода. Формат - обычный текст, агент сам раскладывает его на шаги и показывает разложение до исполнения.
3. Доказательства вместо слов. Каждый шаг подтверждён скриншотом, размером файла на диске, живым PID или дампом UI. «Прошло» без прогона профиль запрещает заявлять.
4. Понятно, чем гонять UI, и не надо это выяснять заново. Мобилка - claude-in-mobile, web - Playwright. Два тупика (claude-in-chrome и browser-модуль claude-in-mobile) задокументированы вместе с причинами, чтобы никто не наступал второй раз.
5. Есть готовая процедура на деплой новой фичи: сперва обновить `smoke/scenarios.md` под новые экраны и действия, потом полный прогон обоих уровней и пересборка отчёта. Любое падение автоматически уходит в профиль `bug-fix`, а для прода - в `incident`, вместе с диагнозом и скриншотом.
