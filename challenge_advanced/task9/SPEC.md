# SPEC — декомпозиция инференса

Замороженный контракт task9. Пороги и форматы записаны **до** первого замера.

---

## 1. Задача, которая плохо решается одним запросом

Тот же триаж сообщения родителя, что в task7 и task8. Но теперь смотрим на него иначе: не как на
одно решение, а как на цепочку из нескольких.

Одним запросом модель сейчас делает **шесть дел сразу**:

1. разбирает свободный текст
2. извлекает возраст ребёнка
3. находит симптомы и тревожные признаки
4. находит числовые показатели, если они есть
5. выбирает маршрут действия
6. формулирует причину и текст ответа

Это классический случай для декомпозиции: задача не одна, а склейка разнородных подзадач.
Извлечение фактов - это чтение. Выбор маршрута - это решение по правилам. Формулировка ответа - это
генерация текста. Разные задачи, разная цена ошибки, разные требования к модели.

**Наблюдаемое следствие смешивания.** В task8 всплыл дефект: сообщение «Дочке 8 месяцев, плохо спит»
уходило в маршрут «по показателям», хотя показателей в нём нет. Модель, решая всё сразу, приняла
возраст за показатель. При разделении этап разбора честно ответит «показателей нет», и этап решения
уже не ошибётся.

## 2. Вариант A — монолит

Один запрос, один ответ. Ровно то, что работает сейчас в task7.

```
сообщение -> [одна модель, один вызов] -> маршрут + флаги + возраст + уверенность + причина
```

Формат ответа - JSON из пяти полей, как в `task7/SPEC.md` раздел 2.

Это точка отсчёта. Всё, что делает multi-stage, сравнивается с ней.

## 3. Вариант B — три этапа

```
сообщение
  -> этап 1: РАЗБОР      факты из текста, без решений
  -> этап 2: РЕШЕНИЕ     маршрут по фактам, без текста
  -> этап 3: ОТВЕТ       текст родителю по маршруту
```

### Этап 1. Разбор входа

Модель **только извлекает**, ничего не решает. Ей запрещено называть маршрут.

Формат - компактный, по одному полю на строку, без JSON:

```
AGE_MONTHS=8
SYMPTOMS=плохой сон
METRICS=none
DURATION=none
PARENT_STATE=none
QUESTION_TYPE=CARE
```

| Поле | Значения |
|---|---|
| `AGE_MONTHS` | целое 0..60 либо `none` |
| `SYMPTOMS` | до пяти симптомов через точку с запятой, либо `none` |
| `METRICS` | показатели вида `weight=8.1kg;height=68cm;sleep=11h`, либо `none` |
| `DURATION` | сколько длится, свободно коротко, либо `none` |
| `PARENT_STATE` | состояние родителя, если он о себе пишет, либо `none` |
| `QUESTION_TYPE` | `CARE` \| `METRICS` \| `PARENT` \| `OTHER` |

Компактный формат выбран намеренно: он вчетверо короче JSON, и модели труднее свалиться в
рассуждения. Разбор строками устойчивее парсинга JSON на маленьких моделях.

### Этап 2. Решение

На вход - **только факты этапа 1**, исходный текст не передаётся. Это принципиально: этап решает по
структуре, а не по эмоциональной окраске сообщения.

Формат - одна строка:

```
ROUTE=EMERGENCY|CONFIDENCE=0.95|WHY=дыхательная недостаточность
```

`ROUTE` - строго из перечисления шести маршрутов. `CONFIDENCE` - 0.0..1.0. `WHY` - до 100 символов.

### Этап 3. Формирование ответа

На вход - маршрут, факты и причина. Задача - собрать текст для родителя по шаблону маршрута.

Формат - свободный текст, но структура задана маршрутом, как в task7.

## 4. Что меряем

| Метрика | Зачем |
|---|---|
| `accuracy` | Совпадение с золотым маршрутом |
| `missed_emergency` | Пропущенные экстренные случаи. **Блокирующая** |
| `false_emergency` | Ложные тревоги |
| `stage_failures` | Сколько раз этап вернул неразбираемый формат |
| `latency_p50`, `latency_p95` | Полный цикл |
| `cost_usd` | Суммарно по всем этапам |
| `tokens_in`, `tokens_out` | Отдельно по этапам - где расходуется больше |

Отдельно: **на каком этапе ломается**. У монолита ошибка неделима, у цепочки видно, разбор подвёл
или решение.

## 5. Правила замера

- Набор тот же: `../task7/data/cases.jsonl`, 50 кейсов.
- Каждый вариант прогоняется **три раза**, решение по худшему прогону. Урок task7: одиночный замер
  не воспроизводится.
- Монолит и цепочка используют одну и ту же модель, иначе сравнение нечестное. Разные модели по
  этапам - отдельный эксперимент поверх, не вместо.
- Температура 0 на всех этапах, кроме случаев, где явно указано иное.

## 6. Гипотезы, которые проверяем

Записаны заранее, чтобы потом не подгонять объяснение под результат.

1. **Цепочка точнее на пограничных случаях**, потому что этап решения работает со структурой, а не с
   формулировками. Ожидаем прирост на группе `borderline`.
2. **Цепочка дороже и медленнее**, потому что три вызова вместо одного. Ожидаем рост стоимости
   примерно втрое.
3. **Цепочка устойчивее к шуму**, потому что этап разбора нормализует вход. Ожидаем прирост на
   группе `noisy`.
4. **Цепочка чинит дефект с показателями**: `QUESTION_TYPE` отделяет вопрос про уход от вопроса про
   цифры на этапе, где решение ещё не принимается.

Если какая-то гипотеза не подтвердится - записываем как есть. Отрицательный результат тут так же
ценен: он покажет, что декомпозиция не бесплатна и не всегда оправдана.
