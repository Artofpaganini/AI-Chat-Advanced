# SPEC — контракт роутинга между моделями

Замороженный контракт task8. Пороги и правила записаны **до** первого замера.
Задача решения та же, что в task7 — триаж сообщения родителя. Меняется не задача, а то, **какая
модель** на неё отвечает.

---

## 1. Зачем роутинг

Из замеров task7:

| Модель | accuracy | пропущено экстренных | цена за 50 кейсов | p50 |
|---|---|---|---|---|
| Qwen3-1.7B дообученная, локально | 0.8261 | 1 | 0 | 1423 мс |
| deepseek-v4-flash, облако | 0.8696 | 0 | 0.0014 USD | 1573 мс |

Сильная модель точнее, но за неё платят. Дешёвая бесплатна, но теряет один экстренный случай.
Роутер должен взять точность сильной по цене, близкой к дешёвой: рутину оставить внизу, спорное
поднять наверх.

**Главный вопрос замера:** какую долю запросов можно оставить на дешёвой модели, не потеряв в
качестве.

---

## 2. Каскад

```
запрос
  -> [pre-routing]   решение по самому тексту, до любого вызова модели
  -> [дешёвая модель] Qwen3-1.7B локально, стоит 0
  -> [post-routing]  решение по её ответу
  -> [сильная модель] deepseek-v4-flash, только если нужно
  -> ответ
```

Уровень 1 отвечает всегда, кроме случая, когда pre-routing сразу отправил наверх.
Уровень 2 включается только по эвристике. Ответ сильной модели считается окончательным — третьего
уровня нет.

---

## 3. Эвристики эскалации

Пять правил. Каждое включается отдельно, чтобы можно было сравнить их между собой, и все вместе.

| Код | Когда срабатывает | Тип | Стоит ли дешёвого вызова |
|---|---|---|---|
| `E_CONF` | `confidence` дешёвой модели ниже порога | post | да |
| `E_STATUS` | статус дешёвой модели `UNSURE` или `FAIL` | post | да |
| `E_GUARD` | ответ дешёвой модели не прошёл проверки формата | post | да |
| `E_RISK` | в тексте запроса есть признак риска | **pre** | **нет, экономит вызов** |
| `E_LEN` | ответ дешёвой модели аномально короткий или длинный | post | да |

`E_RISK` принципиально отличается: смотрит на **вопрос**, а не на ответ. Если в сообщении есть слова
про дыхание, судороги, возраст младше трёх месяцев — спрашивать дешёвую модель смысла нет, сразу
наверх. Это экономит один вызов и снижает задержку на самых важных случаях.

Порог для `E_CONF` прогоняется в нескольких значениях: **0.50, 0.65, 0.75, 0.85, 0.95**. Из этого
получается кривая «сколько сэкономили против сколько потеряли в качестве».

Границы для `E_LEN`: ответ короче 40 или длиннее 1500 символов считается подозрительным.

---

## 4. Стратегии, которые сравниваем

| Стратегия | Что делает |
|---|---|
| `only_cheap` | Всё на дешёвой модели. Нижняя граница по цене и по качеству |
| `only_strong` | Всё на сильной. Верхняя граница по качеству и по цене |
| `route_conf` | Эскалация только по уверенности, порог перебирается |
| `route_status` | Эскалация по статусу |
| `route_risk` | Эскалация только по признаку риска в тексте, до вызова |
| `route_all` | Все пять эвристик вместе |

`only_cheap` и `only_strong` — не стратегии роутинга, а точки отсчёта. Без них цифры роутера не с чем
сравнивать.

---

## 5. Что меряем

| Метрика | Смысл |
|---|---|
| `escalated_share` | Доля запросов, ушедших на сильную модель |
| `stayed_share` | Доля, оставшаяся на дешёвой |
| `accuracy` | Доля совпадений с золотым маршрутом |
| `missed_emergency` | Пропущенные экстренные случаи. **Блокирующая метрика, цель — ноль** |
| `false_emergency` | Ложные тревоги, цена безопасности |
| `cost_usd` | Суммарная стоимость. Дешёвая модель локальна, её вызовы стоят 0 |
| `saved_vs_strong` | Насколько дешевле, чем гонять всё через сильную модель |
| `latency_p50`, `latency_p95` | По полному циклу, включая оба вызова при эскалации |
| `calls_cheap`, `calls_strong` | Сколько вызовов каждого уровня |
| `escalation_reasons` | Разбивка по кодам: какая эвристика сколько раз сработала |

Отдельно считается **польза эскалации**: из тех запросов, что ушли наверх, в скольких сильная модель
дала маршрут, отличный от дешёвой, и в скольких он оказался ближе к золотому. Эскалация, которая ни
разу не поменяла ответ, — потраченные деньги.

---

## 6. Правила замера

- Набор тот же, что в task7: `../task7/data/cases.jsonl`, 50 кейсов, три группы сложности.
- Кейсы с `expected_status = FAIL` (пустой ввод, мусор) из подсчёта точности исключаются, как и в task7.
- Каждая стратегия прогоняется **три раза**. Решение принимается по худшему прогону, а не по лучшему —
  урок task7, где одиночный замер дважды давал невоспроизводимый результат.
- Дешёвая модель — с адаптером `~/models/alva-triage-qwen-lora`, чекпоинт 300. Он выбран замером
  поведения, а не по минимуму validation loss.
- Ключи только из окружения или `local.properties`. В артефакты и логи не попадают.

---

## 7. Что считается успехом

Роутер удался, если одновременно:

1. `missed_emergency` не хуже, чем у `only_strong`
2. `accuracy` не ниже, чем у `only_cheap`
3. `cost_usd` заметно ниже, чем у `only_strong`

Если хоть одно не выполняется — так и записываем. Роутер, который экономит деньги ценой пропущенного
экстренного случая, для этой задачи не имеет смысла.
