# REPORT — роутинг между моделями

Задача task8. Ветка `task8` от `task7`. Контракт в `SPEC.md`, заморожен до первого замера.
Набор кейсов и харнесс переиспользованы из task7, а не написаны заново.

---

## 1. Что построено

Двухуровневый каскад с пятью правилами эскалации.

```
запрос
  -> pre-routing    решение по тексту запроса, ДО любого вызова модели
  -> дешёвый уровень  Qwen3-1.7B дообученная, локально, стоит 0
  -> post-routing   решение по ответу дешёвой модели
  -> сильный уровень  deepseek-v4-flash, только если сработала эвристика
```

| Код | Когда срабатывает | Тип |
|---|---|---|
| `E_RISK` | В тексте запроса есть признак риска | pre, экономит дешёвый вызов |
| `E_CONF` | Уверенность дешёвой модели ниже порога | post |
| `E_STATUS` | Статус дешёвой модели `UNSURE` или `FAIL` | post |
| `E_GUARD` | Ответ не прошёл проверки формата | post |
| `E_LEN` | Ответ аномально короткий или длинный | post |

## 3. Находки

### А. Большая часть эскалаций не меняет ответ

Метрика пользы эскалации для стратегии по риску:

```
эскалировано 31, маршрут поменялся 6, стало точнее 3, стало хуже 1, впустую 25
```

**25 эскалаций из 31 — потраченные деньги.** Сильная модель подтвердила то, что уже сказала дешёвая.
Полезными оказались 3 случая из 31, и один экстренный случай эскалация действительно спасла.

Это главный практический вывод: эскалировать надо реже и точнее. Роутер, который поднимает наверх две
трети трафика, экономит мало и по сути превращается в сильную модель с лишним шагом.

### Б. Роутинг по статусу теряет экстренный случай

Стратегия `route_status` эскалирует всего 6% запросов и экономит 93% — самая дешёвая из всех.
Но она же единственная, что провалила гейт: один пропущенный экстренный случай против нуля у сильной
модели.

Причина в том, что статус дешёвой модели почти всегда `OK`: дообученная модель уверена в себе. Сигнал,
который почти не срабатывает, не может служить защитой.

### В. Температура 0 не гарантирует воспроизводимость

Самое неожиданное. При повторных прогонах роутер в одном случае из трёх терял экстренный случай, а
сильная модель в шести прогонах подряд не теряла ни разу. Выглядело как дефект роутинга.

Разбор показал обратное. Оба пропуска произошли на кейсах, которые роутер **корректно эскалировал**:

```
borderline_08   эскалирован: да, причина E_RISK, вызовов дешёвой 0, сильной 1
                ответ сильной модели: DOCTOR_SOON вместо EMERGENCY
```

Сравнение того же кейса напрямую и через роутер:

```
напрямую:  prompt_tokens 800, кэш 768, ответ 87 токенов -> EMERGENCY
роутер:    prompt_tokens 800, кэш 768, ответ 93 токена  -> DOCTOR_SOON
```

Запрос идентичен: та же модель, та же температура 0, тот же промпт, тот же объём кэша. Ответы разные.

**Облачная MoE-модель недетерминирована даже при температуре 0.** Какие эксперты активируются, зависит
от состава батча на стороне провайдера, а батч складывается из чужих запросов, пришедших одновременно.
Совпадение шести прогонов `only_strong` было везением, а не стабильностью.

Практическое следствие: воспроизводимость нельзя обеспечить настройкой температуры. Для задач, где
ошибка недопустима, это означает, что одиночный ответ облачной модели сам по себе не является
надёжным, независимо от того, насколько она сильная.

### Г. Pre-routing экономит вызов, а не только деньги

`E_RISK` работает по тексту запроса и не тратит дешёвый вызов вовсе: при 31 эскалации дешёвый уровень
вызывался всего 19 раз из 50. Отсюда и задержка ниже, чем у роутинга по уверенности (1418 против
1561 мс), хотя наверх уходит больше запросов.

Правило, которое смотрит на вопрос, дешевле правила, которое смотрит на ответ.

## 4. Ответы на вопросы задания

**Какие запросы остались на маленькой модели.** При стратегии со всеми эвристиками — 32%: бытовые
вопросы про сон, кормление, развитие, а также заведомо посторонние сообщения. Всё, где в тексте нет
признака риска и где дешёвая модель ответила уверенно и в правильном формате.

**Какие ушли на большую.** 68%: всё с признаком риска в тексте (дыхание, судороги, возраст младше трёх
месяцев, температура, сыпь, травма), плюс случаи с низкой уверенностью или сломанным форматом ответа.

**Fallback-логика.** Ответ сильной модели считается окончательным. Если сильная модель не ответила
из-за сбоя, а дешёвая ответила, берётся ответ дешёвой, а причина записывается в поле `error` — иначе
сетевой сбой засчитывался бы как пропущенный экстренный случай.

## 5. Ограничения

- **Тест перекошен в сторону сложного.** 30 кейсов из 50 — пограничные и шумные. В реальном трафике
  доля рутины выше, поэтому экономия там будет больше 28%.
- **46 оцениваемых кейсов.** Разница в один кейс двигает точность на 2 пункта.
- **Недетерминизм сильной модели** делает сравнение стратегий по блокирующей метрике ненадёжным при
  трёх прогонах. Нужны десятки.
- **Пороги 0.50 и 0.65 мертвы** на дообученной модели. Заранее этого знать было нельзя, но в контракте
  они остались.

## 6. Что делать дальше

1. **Сузить эскалацию.** 25 из 31 эскалаций впустую. Стоит попробовать более узкий набор признаков
   риска и посмотреть, сколько полезных эскалаций сохранится.
2. **Комбинировать pre и post.** Сейчас `E_RISK` отправляет наверх, не спрашивая дешёвую модель. Можно
   наоборот: спросить дешёвую и эскалировать только при её сомнении, оставив pre-правило лишь для
   самых явных признаков.
3. **Мерить на десятках прогонов**, а не на трёх. Недетерминизм облачной модели этого требует.
4. **Проверить на реалистичном распределении трафика**, где рутины больше половины.

## 7. Как воспроизвести

```bash
cd challenge_advanced/task8

python3 harness/run_router.py --dry-run --strategy all      # план, без сети
python3 harness/run_router.py --strategy only_cheap          # точка отсчёта снизу
python3 harness/run_router.py --strategy only_strong         # точка отсчёта сверху
python3 harness/run_router.py --strategy route_all           # роутер
python3 harness/router_report.py raw                         # сводка и гейт
```

Дешёвый уровень требует поднятого `mlx_lm.server` на 127.0.0.1:8081 с моделью
`mlx-community/Qwen3-1.7B-4bit`. Адаптер `~/models/alva-triage-qwen-lora` передаётся полем `adapters`
в теле запроса. Ключ сильного уровня берётся из окружения или `local.properties`.
