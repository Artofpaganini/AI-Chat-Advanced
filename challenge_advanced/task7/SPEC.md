# SPEC — контракт задачи и политика уверенности

Замороженный контракт task7. Всё остальное в задаче ссылается сюда, а не переопределяет.
Пороги и правила записаны **до** первого замера — иначе метрика подгоняется под результат.

---

## 1. Задача, где ошибка недопустима

**Триаж входящего сообщения родителя -> решение о действии.**

Ассистент ALVA получает свободный текст от родителя и должен решить, что с этим делать.
Это не генерация текста, а классификация плюс выбор действия. Ровно тот случай, который просит
задание: результат либо верный, либо опасный.

| Маршрут | Что значит | Действие приложения |
|---|---|---|
| `EMERGENCY` | Признаки состояния, угрожающего жизни | Экран скорой помощи, номер 103, совет не ждать |
| `DOCTOR_SOON` | Нужен врач в ближайшее время, но не экстренно | Предложить запись к педиатру |
| `SELF_CARE` | Обычный родительский вопрос | Обычный ответ ассистента |
| `OFF_TOPIC` | Не про ребёнка и не про здоровье | Вежливый отказ |

### Почему ошибка недопустима

Стоимость ошибки **несимметрична**:

- **Пропуск экстренного случая** (`EMERGENCY` распознан как `SELF_CARE`) — ребёнок не попал к врачу.
  Это катастрофа, цена которой не измеряется деньгами.
- **Ложная тревога** (`SELF_CARE` поднят до `EMERGENCY`) — родитель зря понервничал и, возможно, зря
  съездил в приёмный покой. Неприятно, но обратимо.

Отсюда главное правило всей системы: **при любом сомнении маршрут поднимается вверх, а не вниз.**
Мы сознательно платим ложными тревогами за отсутствие пропусков.

## 2. Формат ответа модели

Модель обязана вернуть **только** JSON-объект, без обрамляющего текста и без markdown-заборов.

```json
{
  "route": "EMERGENCY",
  "red_flags": ["затруднённое дыхание", "синюшность губ"],
  "age_months": 8,
  "confidence": 0.93,
  "reason": "Дыхательная недостаточность у грудного ребёнка"
}
```

| Поле | Тип | Правило |
|---|---|---|
| `route` | string | Строго одно из четырёх значений таблицы выше |
| `red_flags` | list[string] | От 0 до 5 элементов, каждый до 60 символов |
| `age_months` | int или null | 0..60, либо null если возраст в сообщении не указан |
| `confidence` | float | 0.0..1.0, собственная оценка модели |
| `reason` | string | 3..200 символов, одна фраза |

---

## 3. Механизм 1 — Constraint-based

Проверки, которые не требуют второго вызова модели. Дешёвые, детерминированные, ловят мусор до того,
как он дойдёт до пользователя.

**Проверки формата**

| Код | Что проверяет |
|---|---|
| `C_JSON` | Ответ парсится как JSON-объект |
| `C_KEYS` | Ровно пять ключей из таблицы, ни больше ни меньше |
| `C_TYPES` | Типы полей совпадают с контрактом |

**Проверки допустимых значений**

| Код | Что проверяет |
|---|---|
| `C_ROUTE_ENUM` | `route` входит в перечисление |
| `C_CONF_RANGE` | `confidence` в отрезке 0..1 |
| `C_AGE_RANGE` | `age_months` в 0..60 либо null |
| `C_FLAGS_SHAPE` | `red_flags` — список строк, не длиннее 5, элементы до 60 символов |
| `C_REASON_LEN` | `reason` от 3 до 200 символов |

**Логические инварианты**

| Код | Инвариант | Зачем |
|---|---|---|
| `C_INV_EMERGENCY_FLAGS` | `route = EMERGENCY` -> `red_flags` непустой | Экстренный маршрут обязан назвать причину |
| `C_INV_SELFCARE_FLAGS` | `route = SELF_CARE` -> `red_flags` пустой | Нельзя одновременно видеть тревожный признак и советовать домашний уход |
| `C_INV_OFFTOPIC_CLEAN` | `route = OFF_TOPIC` -> `red_flags` пустой и `age_months` = null | Не про ребёнка — значит нет ни возраста, ни симптомов |
| `C_INV_CONF_FLOOR` | `route = EMERGENCY` -> `confidence >= 0.5` | Неуверенная экстренность — сигнал разобраться, а не принять молча |

Нарушение любого инварианта -> **один** повторный вызов с указанием, что именно нарушено.
Второе нарушение -> статус `FAIL`, ответ модели отбрасывается.

---

### 3.1 Предусловия входа

Дополнение к контракту, внесено 2026-07-28 **после** первого замера. Основание — найденный дефект, а не
желание улучшить цифру. Первый прогон показал: на пустой строке модель вернула `EMERGENCY` с
уверенностью 0.822 и двумя голосами из трёх, и система приняла это как достоверный результат.
Повторы тут бессильны — модель уверенно галлюцинирует одинаково.

Вывод: проверять только выход недостаточно. Вход тоже обязан проходить проверку, причём **до** вызова
модели.

| Код | Условие | Реакция |
|---|---|---|
| `C_IN_EMPTY` | Строка пустая или состоит только из пробельных символов | `FAIL` без единого обращения к модели |
| `C_IN_NO_LETTERS` | В строке нет ни одной буквы любого алфавита | `FAIL` без единого обращения к модели |

Отказ по предусловию стоит ноль вызовов и ноль денег. Это самый дешёвый вид контроля из всех
четырёх механизмов, и он же ловит самый опасный класс отказа — уверенную выдумку на пустоте.

Граница проверки намеренно узкая. `C_IN_NO_LETTERS` не пытается судить о смысле: строка `asdfgh 12345`
буквы содержит и до модели дойдёт. Расширять правило до распознавания бессмыслицы — значит подгонять
проверку под конкретные тестовые кейсы, а такая проверка не переживёт встречу с реальным трафиком.

## 4. Механизм 2 — Redundancy

Один и тот же запрос выполняется **3 раза** при `temperature = 0.7`. Разброс сэмплов показывает,
насколько решение устойчиво.

| Согласие голосов | Трактовка |
|---|---|
| 3 из 3 | Решение устойчивое |
| 2 из 3 | Есть сомнение |
| 1 / 1 / 1 | Консенсуса нет |

Итоговый маршрут — **не простое большинство**. Применяется несимметричное правило безопасности:

```
severity: EMERGENCY = 3 > DOCTOR_SOON = 2 > SELF_CARE = 1 > OFF_TOPIC = 0

route_final = max(severity) по всем валидным голосам
```

То есть **одного голоса за `EMERGENCY` достаточно**, чтобы маршрут стал экстренным. Согласие при этом
всё равно записывается — оно влияет на статус и на то, покажем ли мы пометку «проверьте сами».

Голоса, не прошедшие constraint-проверку, из голосования выбывают. Если валидных голосов не осталось —
сразу `FAIL`.

---

## 5. Механизм 3 — Self-check

Второй проход, в котором модель выступает критиком собственного результата. Запускается
**адаптивно** — только когда голосование дало согласие ниже полного (2 из 3 или хуже), либо когда
сработал safety-подъём маршрута. На единогласных случаях этот вызов не тратится.

Критик получает исходное сообщение и предложенный маршрут, и возвращает:

```json
{"verdict": "AGREE", "risk_missed": false, "note": "коротко почему"}
```

| Поле | Значение |
|---|---|
| `verdict` | `AGREE` или `DISAGREE` |
| `risk_missed` | true, если критик видит опасный признак, который первый проход упустил |
| `note` | до 200 символов |

`risk_missed = true` **всегда** поднимает маршрут до `EMERGENCY` и ставит статус `UNSURE`, каким бы ни
было голосование. Это последний предохранитель.

---

## 6. Механизм 4 — Scoring и статус

Итоговая уверенность собирается из трёх сигналов:

```
confidence_final = 0.5 * vote_agreement
                 + 0.3 * self_check_agreement
                 + 0.2 * mean(self_reported_confidence)
```

- `vote_agreement` — доля голосов за итоговый маршрут: 1.0 при 3 из 3, около 0.67 при 2 из 3, 0.33 при полном разбросе.
- `self_check_agreement` — 1.0 при `AGREE`, 0.0 при `DISAGREE`. Если self-check не запускался, берётся `vote_agreement`, чтобы пропуск шага не давал бесплатной прибавки.
- `self_reported_confidence` — среднее поле `confidence` по валидным голосам.

**Пороги (заданы до замера):**

| Статус | Условие | Что делает приложение |
|---|---|---|
| `OK` | `confidence_final >= 0.75` и нет неустранённых нарушений | Показывает ответ как есть |
| `UNSURE` | `0.40 <= confidence_final < 0.75`, либо сработал safety-подъём, либо `risk_missed` | Показывает ответ с явной пометкой о неуверенности и советом проверить у врача |
| `FAIL` | `confidence_final < 0.40`, либо не осталось валидных голосов | Ответ не показывается. Отдаётся безопасная заглушка: «не могу разобрать вопрос, при тревоге обратитесь к врачу» |

`FAIL` — это не поломка, а штатный отказ отвечать. Для задачи, где ошибка недопустима, молчание
лучше уверенной чепухи.

**Что значит «неустранённое нарушение».** Уточнение внесено 2026-07-28 после ревью, где эта строка
читалась двояко. Нарушение, которое починил повторный вызов, статус не понижает: сэмпл вернулся в
голосование валидным, и дальше он ничем не отличается от сэмпла, который был валиден сразу. Понижают
статус только те нарушения, которые пережили ремонт — из-за них сэмпл выбывает из голосования.

Пример из данных: у кейса `clean_02` записано `retried = true` и два нарушения формата, но статус
`OK` при уверенности 0.992. Это ожидаемое поведение, а не дефект. Поле `violations` при этом хранит
всю историю целиком, включая починенное, — иначе в отчёте было бы не видно, как часто модель вообще
промахивается мимо формата.

## 7. Наборы для проверки

| Группа | Сколько | Что проверяет |
|---|---|---|
| `clean` | 20 | Однозначные случаи всех четырёх маршрутов |
| `borderline` | 15 | Реально пограничные: температура на возрастной границе, вялость без других признаков |
| `noisy` | 15 | Опечатки, обрывки, эмодзи, смешанный язык, противоречия внутри сообщения, попытка перехвата промпта, пустой ввод, очень длинный текст |

Каждый случай несёт золотую разметку `expected_route` и поле `why_hard`.

Для группы `noisy` у части случаев ожидание — не маршрут, а **статус**: правильное поведение на
пустом вводе это `FAIL`, а не угадывание.

---

## 8. Что меряем

| Метрика | Как считаем |
|---|---|
| `accuracy` | Доля совпадений с золотым маршрутом |
| `missed_emergency` | Сколько раз золотой `EMERGENCY` получил маршрут ниже. **Главная метрика, целевое значение — ноль** |
| `false_emergency` | Сколько раз не-экстренный случай поднят до `EMERGENCY`. Цена безопасности |
| `rejected` | Сколько ответов отклонено со статусом `FAIL` |
| `unsure` | Сколько ушло в `UNSURE` |
| `retried` | Сколько случаев потребовали повторного вызова из-за нарушения ограничений |
| `extra_calls` | Сколько всего дополнительных вызовов модели сверх одного |
| `latency_p50/p95` | По полному циклу принятия решения |
| `cost` | Токены на вход и выход, умноженные на цену модели |

Всё это считается дважды: для **baseline** (один вызов, никакого контроля) и для **pipeline**
(полный цикл). Смысл задачи — в разнице между этими двумя колонками.
