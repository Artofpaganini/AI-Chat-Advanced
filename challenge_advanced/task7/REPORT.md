## 1. Что за задача и почему ошибка недопустима

Триаж входящего сообщения родителя в приложении ALVA: свободный текст -> решение о действии.

| Маршрут | Действие приложения |
|---|---|
| `EMERGENCY` | Экран скорой, совет не ждать |
| `DOCTOR_SOON` | Предложить запись к педиатру |
| `SELF_CARE` | Обычный ответ ассистента |
| `OFF_TOPIC` | Вежливый отказ |

Цена ошибки несимметрична. Пропустить экстренный случай — ребёнок не попал к врачу. Поднять ложную
тревогу — родитель зря понервничал. Поэтому вся система устроена так, чтобы при сомнении маршрут шёл
вверх, а не вниз. Сколько это стоит в ложных тревогах — меряется отдельной метрикой, чтобы цена не
пряталась.

Дообучение не применялось. Вся уверенность строится вокруг готовой модели.

## 2. Четыре механизма

| Механизм | Что ловит | Чего не видит |
|---|---|---|
| Constraint-based | Сломанный JSON, нарушенный инвариант, негодный вход | Правдоподобную ошибку внутри валидного ответа |
| Redundancy, 3 сэмпла при t=0.7 | Неустойчивое решение | Три одинаково неверных ответа |
| Self-check, критик | Упущенный опасный признак | Согласованную слепоту модели, если не позван |
| Scoring | Сводит сигналы в `OK` / `UNSURE` / `FAIL` | Ничего сам по себе, он только агрегатор |

Голосование идёт **не по большинству, а по максимуму тяжести**: одного голоса за `EMERGENCY`
достаточно, чтобы поднять маршрут. Простое большинство глушит одиночный сигнал тревоги, а для этой
задачи это неверно.

## 4. Находки

### А. Уверенная выдумка на пустом входе

Первый прогон, до того как в контракте появились предусловия:

```
вход: пустая строка
выход: route EMERGENCY, status OK, confidence 0.822
голоса: [EMERGENCY, EMERGENCY, SELF_CARE]

вход: строка из пробелов
выход: route SELF_CARE, status OK, confidence 0.93
голоса: [SELF_CARE, SELF_CARE, SELF_CARE]
```

Модель на пустоте выдумала экстренную ситуацию, а система приняла это как достоверный результат.
Повторы тут бесполезны: модель галлюцинирует уверенно и одинаково, согласие голосов только укрепляет
ложную уверенность.

Вывод: проверять один лишь выход недостаточно. Вход обязан проверяться тоже, и это самый дешёвый
механизм из всех — отказ по предусловию стоит ноль вызовов.

После добавления предусловий (`C_IN_EMPTY`, `C_IN_NO_LETTERS`):

| | было | стало |
|---|---|---|
| accuracy | 0.8696 | 0.8913 |
| отклонено | 0 | 3 |
| сэкономлено вызовов | 0 | 9 |
| ложных EMERGENCY | 5 | 3 |

Граница проверки намеренно узкая. Строка `asdfgh 12345` буквы содержит и до модели доходит.
Расширять правило до распознавания бессмыслицы — значит подгонять его под тестовые кейсы.

### Б. На сильной модели контроль не поднимает точность

На DeepSeek `missed_emergency` равен нулю и с контролем, и без. Контроль не сделал модель умнее.
Его польза в другом: 2 шатких решения помечены `UNSURE`, 3 негодных входа отклонены. Это не
«улучшение качества», это честная разметка того, где модели нельзя верить.

На gpt-4o-mini контроль точность даже **снизил**: 0.8261 -> 0.7826. Причина — safety-подъёмы: маршрут
поднимается выше золотого, и формально это считается ошибкой. Так и задумано, но цену видно.

### В. Уверенность не равна правильности

Главный результат. **Ни на одном из трёх стендов контроль не уменьшил число пропущенных экстренных
случаев:** 0 -> 0, 3 -> 3, 4 -> 4.

Все пропуски выглядят одинаково:

```
borderline_08  рвота фонтаном у ребёнка 5 недель (признак пилоростеноза, по разметке EMERGENCY)
  route DOCTOR_SOON, голоса 3/3, confidence 0.974, критик не запускался

borderline_06  красные точки на голенях, родитель не понимает, бледнеют ли
  route DOCTOR_SOON, голоса 3/3, confidence 0.943, критик не запускался
```

Голоса единогласны, уверенность выше 0.94, критик по правилу адаптивности не позван — **именно
потому, что голоса сошлись**.

Redundancy ловит **неустойчивость**, а не **незнание**. Если модель не знает, что рвота фонтаном у
пятинедельного ребёнка это экстренный случай, она не знает этого стабильно, и все три сэмпла
согласятся. Три уверенных голоса за неверный ответ выглядят точно так же, как три уверенных голоса за
верный.

### Г. Адаптивность критика оказалась ловушкой, но лечение хуже болезни

Гипотезу из находки В проверили экспериментом: критик запускается на **каждом** кейсе, независимо от
согласия голосов. Прогон на gpt-4o-mini, артефакт `raw/pipeline_runs_gpt4omini_forced.jsonl`.

| Режим критика | accuracy | пропущено EMERGENCY | ложных EMERGENCY | вызовов | стоимость |
|---|---|---|---|---|---|
| адаптивный | 0.7826 | 3 | 2 | 149 | 0.0211 |
| принудительный | 0.6304 | **0** | **15** | 191 | 0.0249 |

Пропуски обнулились. Но ложные тревоги выросли с 2 до 15 из 46 — почти треть. Принудительный критик
поднял до `EMERGENCY` в том числе `noisy_15`, где вход это мусор `asdfgh 12345`.

Из трёх ранее пропущенных случаев критик спас напрямую **один** (`borderline_06`, вердикт `DISAGREE`
с `risk_missed`). Два других поднялись потому, что голоса при температуре 0.7 во втором прогоне легли
иначе. Приписывать критику все три было бы неверно.

Практический вывод: триггер критика по согласию голосов — плохой. Но и «звать всегда» не годится.
Нужен триггер по признаку риска в самом сообщении (возраст младше 3 месяцев, дыхание, судороги,
сыпь), а не по разбросу ответов модели.

### Д. Одиночный замер не воспроизводится, и я сам на этом попался

Четыре прогона одного и того же кода на тех же 50 кейсах, между ними не менялось ничего.

Размах точности — 8.7 процентных пункта, медиана 0.8043. Маршрут менялся у 6 кейсов из 50.
Лучший прогон выпал один раз из четырёх, и именно он попал в первую версию этого отчёта.

Главное: **блокирующая метрика не устояла.** В разделе 3 записано `пропущено EMERGENCY = 0` по

То есть вывод «на DeepSeek контроль не пропускает экстренные случаи» был сделан по одной точке и

Практический вывод: для метрики, где ошибка недопустима, единичный прогон при температуре 0.7 не
является измерением. Нужно N прогонов, и решение принимается по **худшему** результату, а не по

Артефакты: `raw/pipeline_runs_rep1.jsonl`, `rep2`, `rep3`.

Про самый первый замер: его сырой файл был затёрт последующим прогоном, уцелел только агрегат —

надо разводить по именам сразу, а не перезаписывать один файл.

### Е. Помогает не самопроверка, а проверка другой моделью

Из находки Г следовал вопрос: критик — та же самая модель с другим промптом. Может ли он вообще дать
независимый сигнал, если ошибается там же, где ошибается основной проход.

Проверили: генератор `gpt-4o-mini`, критик `deepseek-chat`, триггер по риску. Три прогона каждого
варианта, потому что после находки Д одной точке мы больше не верим.

| Критик | accuracy | пропущено EMERGENCY | ложных тревог | несогласий критика |
|---|---|---|---|---|
| та же модель, триггер по разбросу | 0.7826 | 3 | 2 | 0 из 3 запусков |
| та же модель, триггер по риску | 0.6957 | 0 | 13 | 13 из 32 |
| **другая модель, триггер по риску** | 0.7826 .. 0.8261 | 0 / 1 / 2 по прогонам | **3, 3, 3** | 2 из 31 |

Что здесь правда, а что нет.

**Правда и воспроизводимо:** чужой критик резко дешевле по ложным тревогам — ровно 3 во всех трёх
прогонах против 13 у самопроверки. Он не согласился всего дважды из 31 запуска, и обе претензии
оказались по делу. Своя же модель, когда её просят проверить себя, несогласна в 13 случаях из 32, и
12 из них — ложная тревога. Самопроверка не даёт независимого сигнала: модель не видит собственную
слепую зону и компенсирует это перестраховкой.

**Неправда:** «чужой критик убирает пропуски». В первом прогоне их было ноль, и на этом можно было бы
остановиться и объявить победу. Повторы дали 1 и 2. Худший случай — два пропуска, то есть проблема из
находки В **не решена**, она лишь стала дешевле по ложным тревогам.

Отдельно стоит отметить: я поймал себя на этой ошибке дважды за одну задачу — в разделе 3 и здесь.
Соблазн взять лучший прогон и объявить результат очень силён, потому что первый замер почти всегда
выглядит убедительно.

#### То же самое на слабой модели, и там результат сильнее

Тот же опыт повторили на локальной Qwen3-1.7B, по два прогона на вариант.

| Вариант | accuracy | пропущено EMERGENCY | ложных тревог |
|---|---|---|---|
| без критика, триггер по разбросу | 0.6087 | 4 | 5 |
| критик — та же Qwen | 0.5870 / 0.5870 | 0 / 0 | 12 / 14 |
| **критик — deepseek** | 0.6304 / 0.6522 | **0 / 0** | **8 / 8** |

Здесь чужой критик убрал все четыре пропуска **устойчиво, в обоих прогонах**, и при этом поднял
точность, а не уронил. На gpt-4o-mini того же не вышло: там пропуски гуляли 0, 1, 2.

Отсюда закономерность, которую видно на двух генераторах сразу: **чем грубее ошибается модель, тем
надёжнее её ловит независимый судья.** Слабая модель ошибается заметно, и сильный судья это видит.
Сильная модель ошибается тонко, на пограничных случаях, где судья и сам не уверен.

Практический вывод для продукта: связка «дешёвая быстрая модель + сильный независимый судья по
признаку риска» выглядит осмысленнее, чем одна сильная модель, проверяющая саму себя. На Qwen такая
связка дала 0 пропусков при 8 ложных тревогах, тогда как самопроверка той же Qwen — 0 пропусков при
12-14 ложных.

Артефакты: `raw/pipeline_runs_qwen_crosscritic.jsonl`, `_crosscritic2`, `_samecritic`, `_samecritic2`.

### Ж. То, что не смог контроль, смогло дообучение

Находка В упёрлась в предел: контроль не лечит незнание модели. Проверили прямо — вылечили незнание.

Дообучили `Qwen3-1.7B-4bit` через LoRA на 260 примерах триажа. Обучающий набор написан отдельно и
**не пересекается** с тестовым: максимальный коэффициент Жаккара 0.382 при пороге 0.6, точных
совпадений ноль. Тест остался тем же самым, что и во всех замерах выше, и цифры «до» получены
задолго до того, как возникла мысль дообучать.

| Вариант | accuracy | пропущено EMERGENCY | ложных тревог | p50 |
|---|---|---|---|---|
| Qwen база | 0.6087 | 4 | 6 | 1628 мс |
| Qwen база + контроль | 0.6087 | 4 | 5 | 9298 мс |
| **Qwen дообучена** | **0.8043 .. 0.8261** | **1, устойчиво в 3 прогонах** | 4-5 | **1423 мс** |
| Qwen дообучена + контроль | 0.7609 .. 0.8043 | **0, устойчиво в 3 прогонах** | 8-10 | 10674 мс |
| для сравнения: gpt-4o-mini | 0.8261 | 3 | 1 | 1393 мс |
| для сравнения: deepseek | 0.8696 | 0 | 3 | 1580 мс |

Что из этого следует.

**Дообучение сдвинуло ровно ту метрику, которую контроль не двигал.** Пропуски 4 -> 1, точность
0.6087 -> 0.8261. Контроль на той же базовой модели не менял ни то, ни другое.

**Локальная модель на 1.7B догнала облачную.** Дообученная Qwen даёт ту же точность, что
`gpt-4o-mini` (0.8261 у обеих), и при этом пропускает меньше экстренных случаев: 1 против 3.
Работает локально, быстрее, и не стоит денег за токены.

**Вместе они дают то, чего не даёт ни одно по отдельности.** Дообучение довело пропуски до одного,
контроль поверх дообученной модели убрал последний — ноль в трёх прогонах из трёх. Это первый раз за
всю работу, когда блокирующая метрика держит ноль воспроизводимо. Цена: ложные тревоги удваиваются
(4-5 -> 8-10) и задержка растёт до 10.7 секунды.

#### Валидационная ошибка обманула, причём наоборот

| Чекпоинт | Val loss | accuracy на тесте |
|---|---|---|
| 25 | 0.643 | 0.6957 |
| 50 | **0.571**, минимум | 0.6522 |
| 150 | 0.609 | 0.7826 |
| 300 | **0.740**, худшая | **0.8261** |

Чекпоинт с худшей валидационной ошибкой показал лучшее поведение. Корреляция не слабая, а обратная.
Стандартная практика «взять чекпоинт с минимумом val loss» дала бы 0.6522 вместо 0.8261.

В task6 был похожий урок, но мягче: там минимум val loss просто не совпал с лучшим поведением. Здесь
он указывает прямо в противоположную сторону. Для задач, где важен не язык, а решение, выбирать
чекпоинт нужно замером поведения на отложенном наборе, а не кривой обучения.

#### Где предел дообучения и почему мы остановились

Проверили три вещи после первого успеха, все замером на том же тесте.

| Что меняли | Набор | Ранг | Итераций | accuracy | пропущено |
|---|---|---|---|---|---|
| исходный успех | 260 | 16 | 300 | **0.8261** | 1 |
| дольше учить | 260 | 16 | 500 | 0.7174 | 2 |
| больше данных, меньше ёмкость | 1019 | 8 | 500 | 0.7391 | 1 |
| больше данных, та же ёмкость | 1019 | 16 | — | не досчитано | — |

**Дольше учить — хуже.** На 500 итерациях точность упала на 11 пунктов против 300. Причём по кривой
потерь этого не видно: валидация стояла на плато. Переобучение здесь видно только поведением.

**Расширение набора не дало прироста.** Обучающий набор довели с 260 до 1019 примеров (сборка из
шардов, дедуп, проверка непересечения с тестом). Результат 0.7391 против 0.8261.

Но этот вывод **нельзя считать надёжным**, и вот почему: в том прогоне менялись два параметра сразу —
объём набора вырос вчетверо и ранг адаптера упал вдвое. Признак недообучения налицо: train loss
застрял на 0.477 против 0.090 в удачном прогоне, то есть ёмкости не хватило. Чистый эксперимент
(1019 примеров при ранге 16) мы запустили и **остановили не досчитав**.

Причина остановки честная: тест содержит 46 оцениваемых кейсов, и разница между 0.7391 и 0.8261 —
это **четыре кейса**. При разбросе между одинаковыми прогонами в 8.7 пункта (находка Д) такая разница
неотличима от шума. Дальше имеет смысл расширять не обучающий набор, а **тестовый** — иначе мы
уточняем цифру инструментом, который грубее самой разницы.

Что осталось непроверенным, прямо: помогает ли расширение набора при сохранённой ёмкости адаптера.

Артефакты: `raw/baseline_runs_tuned_*.jsonl`, `raw/baseline_runs_full*.jsonl`,
`raw/pipeline_runs_tuned_pipe*.jsonl`, `raw/train_triage.log`, `raw/train_triage_full.log`,
наборы `data/train_triage.jsonl` (260) и `data/train_triage_full.jsonl` (1019).

## 7. Ограничения

- **Контроль не лечит незнание модели.** Это не недоработка реализации, а свойство подхода. Ни один
  из четырёх механизмов не может отличить уверенный верный ответ от уверенного неверного. Лечится это
  данными, а не контролем - см. находку Ж.
- **Триггер критика неудачен.** Запуск по разбросу голосов не срабатывает там, где нужен. Замена на
  «звать всегда» даёт треть ложных тревог. Нужен триггер по содержанию сообщения.
- **50 кейсов мало.** Разница в 1-2 кейса двигает accuracy на 2-4 процентных пункта. Прогоны при
  температуре 0.7 не воспроизводятся дословно: между двумя прогонами gpt-4o-mini три голоса совпали
  у 45 кейсов из 50.
- **Разметка borderline спорна по своей природе.** Она защитима, но другой педиатр расставил бы
  часть маршрутов иначе.
- **Пороги 0.75 и 0.40 выбраны до замера и не подбирались.** Это честно, но не значит, что они
  оптимальны.

### Только русский язык

Ассистент работает исключительно с русским текстом. Это не настройка, а свойство реализации: все
словари написаны под русские слова - признаки риска `RISK_TRIGGER_PATTERNS`, признаки кризиса
`CRISIS_TRIGGER_PATTERNS`, темы поддержки `SUPPORT_THEME_PATTERNS`, разбор чисел из сообщения
`AGE_PATTERNS` и соседние. Шаблоны ответов тоже написаны по-русски и подстановкой перевода
не лечатся.

На иностранном тексте эти словари не молчат, а срабатывают случайно, и результат непредсказуем.
Три замера на английском, версия v2 до языкового правила:

| Сообщение | Что получилось | Почему плохо |
|---|---|---|
| `My son is 7 months old, breathing hard, lips blue` | EMERGENCY, ответ верный | совпадение, а не работа словаря |
| `We are 7 months old, weigh 8.1 kg, height 68 cm` | цифры не извлечены, ассистент просит прислать возраст и вес | они уже есть в сообщении |
| `I have not slept for four months, I cry every day` | EMERGENCY плюс кризисный протокол с телефоном доверия | по-русски тот же смысл даёт PARENT_SUPPORT, `crisis: false` |

Третий случай - ложная кризисная тревога: вымотанному родителю выдаётся протокол, написанный для
человека с мыслями о самоповреждении. Ошибка в безопасную сторону, но доверие к ассистенту она
убивает.

Поэтому в v2 стоит языковое правило: если в сообщении нет ни одного символа кириллицы, а буквы
есть, запрос отклоняется кодом `C_IN_NOT_RUSSIAN` до обращения к модели - ноль вызовов, ноль денег,
в ответе просьба написать по-русски. Правило терпимо к смешанному тексту: хватит одного русского
слова, поэтому `нам 7 месяцев, temperature 38` и латинские названия лекарств проходят нормально.

Чтобы снять ограничение, недостаточно перевести шаблоны. Нужно: продублировать все четыре словаря
на каждый язык, перевести тексты ответов и, главное, отдельно проверить кризисный детектор на
иноязычном наборе - именно он даёт самую дорогую ошибку. Пока этого нет, честный отказ лучше
случайного срабатывания.

**Отдельный риск этого решения:** родитель, который пишет о кризисе не по-русски, получает отказ
вместо телефона экстренной помощи. Языковой гейт стоит раньше кризисного, иначе английский текст
снова пойдёт в русские словари. Дешёвая страховка - добавить в текст отказа строку с номерами
`8-800-2000-122` и `112`: она ничего не стоит и не требует иноязычных словарей.

## 8. Что делал бы дальше

Пункты 1-3 исходного списка уже проверены по ходу работы, результаты в находках Г, Д, Е. Осталось:

1. **Три сэмпла разными моделями, а не одной при разной температуре.** Находка Е показала, что
   независимость судьи решает многое. Логично применить это и к самому голосованию: сейчас три сэмпла
   одной модели коррелируют и ошибаются вместе.
2. **Калибровка критика.** Чужой критик даёт 3 ложные тревоги стабильно, свой — 13. Стоит замерить
   третью и четвёртую модель в роли судьи: возможно, разброс между судьями больше, чем между
   триггерами.
3. **Набор в 200+ кейсов с разметкой практикующего педиатра.** При 46 оцениваемых кейсах один
   изменившийся кейс двигает точность на 2 пункта, а весь наш разброс — 8.7 пункта.
4. **Решение по худшему прогону, а не по среднему.** Для блокирующей метрики это должно быть зашито в
   сам гейт: N прогонов, берём максимум пропусков.
5. **Сначала тест, потом всё остальное.** Расширять обучающий набор дальше бессмысленно, пока тест
   состоит из 46 оцениваемых кейсов: разница в четыре кейса тонет в разбросе между одинаковыми
   прогонами. Это блокирует любую дальнейшую настройку - и обучения, и порогов, и триггеров.

## 9. Как воспроизвести

```bash
cd challenge_advanced/task7

# план вызовов и оценка стоимости, без сети
python3 harness/run_eval.py --dry-run --mode both

# DeepSeek, ключ берётся из окружения либо из local.properties
python3 harness/run_eval.py --mode both --workers 6
python3 harness/report.py

# gpt-4o-mini
export OPENAI_API_KEY=<ключ>
python3 harness/run_eval.py --mode both --key-env OPENAI_API_KEY \
  --base-url https://api.openai.com/v1 --model gpt-4o-mini \
  --out-suffix _gpt4omini --workers 6
python3 harness/report.py --baseline raw/baseline_runs_gpt4omini.jsonl \
  --pipeline raw/pipeline_runs_gpt4omini.jsonl \
  --out results/confidence_report_gpt4omini.json

# локальная модель, нужен поднятый mlx_lm.server на 8080
python3 harness/run_eval.py --mode both --base-url http://127.0.0.1:8080/v1 \
  --model mlx-community/Qwen3-1.7B-4bit --out-suffix _qwen --workers 3

# эксперимент с принудительным критиком
python3 harness/run_eval.py --mode pipeline --always-self-check \
  --key-env OPENAI_API_KEY --base-url https://api.openai.com/v1 \
  --model gpt-4o-mini --out-suffix _gpt4omini_forced --workers 6

# смоук, гейт по всем механизмам
python3 harness/smoke.py
```

Ключи только из переменных окружения или из `local.properties`, который лежит в `.gitignore`.
В артефакты и логи ключ не попадает: проверено grep-ом при ревью.
