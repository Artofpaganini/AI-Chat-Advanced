# PLAN - шлюз к LLM

Ход работы по task13. Что делаем, в каком порядке, что берём готовым из прошлых задач и что пошло
не так, как задумывалось.

---

## 1. Идея

В приложении уже есть входной и выходной guard (task11, task12), но у него нет ни одного регекса на
секреты, нет проверки карты по Луну, и главное - он выключается флажком в настройках. Защита,
которую выключает сам клиент, не является защитой от злоумышленника по устройству. Нужен рубеж на
сетевой стороне: HTTP-прокси между приложением и DeepSeek, до которого клиент физически не
дотягивается - ключ провайдера живёт только там, секреты фильтруются там, лимит частоты и журнал
аудита - тоже там. Отдельное требование заказчика: результат должен быть виден в самом приложении,
не только в терминале - значит, часть работы это Kotlin, а не только Python.

интеграция в приложение (четвёртый провайдер, баннер, экран журнала).

## 3. Порядок шагов

1. **Разведка.** Сеть приложения (единственная точка выбора адреса - `KoinInitializer.kt:40-77`,
   нестандартное поле `triage` из тринадцати полей, которое нельзя терять при проксировании),
   существующие guard-ы приложения и их дыры (нет регексов на секреты, нет проверки Луна, нет PII на
   входе, выключаются флажком).
2. **`GATEWAY_CONTRACT.md`.** Адрес и порт шлюза, форма ответа служебных эндпоинтов, канал сигналов
   (заголовки `X-Gateway-*`), коды детекторов входа и выхода, коды HTTP-ответов (блокировка - `200`
   с текстом-предупреждением, не `403` - иначе приложение покажет техническую ошибку сети вместо
   объяснения), формат журнала аудита. Заморожено до начала прогонов, правится только через раздел
   «Ревизии» с датой.
3. **Разделение зон между тремя исполнителями**, чтобы не столкнуться на одних файлах:
   A1 - детекторы и гейты (`spec13.py`, `secret_detectors.py`, `input_guard.py`, `output_guard.py`,
   `data/cases.jsonl.b64`, `run_tests.py`), A2 - сервер (`gateway_server.py`, `rate_limit.py`,
   `cost.py`, `audit_log.py`), B - приложение (Kotlin). `spec13.py` пишет только A1.
4. **Первый прогон по dev-набору.** 28 из 28, ноль пропусков, ноль ложных - и сразу видно, что число
   ничего не доказывает: набор писал тот же, кто писал детекторы.
5. **Правка контракта - деление dev/holdout.** `data/holdout_cases.jsonl.b64`, 42 кейса, пишет
   исполнитель, не читавший `harness/`. Прогон - 14 из 31 (45%), одно ложное срабатывание.
6. **A2 подтверждает сервер живым прогоном** против настоящего апстрима: чистый запрос проходит,
   поддельный AWS-ключ блокируется до апстрима, 21-й запрос в минуту получает `429`, опасная команда
   в ответе модели блокируется на выходе. Отдельно - находка про потоковый режим: заголовок ответа
   уходит раньше тела, значит вердикт выходного гейта физически не может попасть в
   `X-Gateway-Verdict`, если поток обрывается позже. Решение - раздел 8.1 контракта, отдельное
   SSE-событие перед `[DONE]`.
7. **Интеграция в приложение.** Четвёртый провайдер «Через шлюз» рядом с тремя существующими,
   `isApiKeyRequired = false` (ключ живёт на шлюзе, это главный смысл задачи), баннер над сообщением
   при срабатывании гейта, экран журнала шлюза, строка со стоимостью и токенами.
8. **Усиление детекторов по классам, без доступа к holdout.** Координатор описывает словами два
   сорта пропусков (законные пробелы покрытия и классы обхода), исполнитель усиления не видит ни
   `holdout_cases.jsonl.b64`, ни его результат. `data/cases.jsonl.b64` вырос с 28 до 64 кейсов - новые
   форматы ключей получили свои dev-проверки.
9. **Второй слепой набор `holdout2_cases.jsonl.b64`**, 50 кейсов от третьего исполнителя, который не
   видел ни кода, ни первых двух наборов. Цифра «после усиления» берётся только с него: 25 из 36
   (69%). Первый слепой набор после усиления - 26 из 31 (84%) - тоже приводится, но с пометкой, что
   он уже участвовал в разборе классов и завышен по построению.
10. **Замер стрима.** Задержка (`buffer` держит ответ целиком, `incremental` отдаёт первый символ
    втрое быстрее) и утечка до обрыва - сначала одна категория (12 знаков), потом все три
    (максимум 815 знаков). Решение по дефолту принято на втором числе, не на первом.
11. **Итоговые документы** - `REPORT.md`, `RESULT.md`, `README.md`, этот `PLAN.md`, `SPEC.md`.

## 4. Развилки и как их закрываем

| Развилка | Решение | Почему |
|---|---|---|
| Какой апстрим проксировать | DeepSeek, не OpenAI | ключ есть только от DeepSeek, формат API совместим с OpenAI, адрес - параметр запуска, в отчёте это сказано прямо, не заминается |
| Каким кодом HTTP отдавать блокировку | `200` с текстом-предупреждением в теле, вердикт - в заголовке | `403` заставил бы приложение показать «что-то сломалось» вместо объяснения; `429` оставлен только для настоящего отказа обслуживания - превышения частоты |
| Как передавать вердикт в приложение, не переписывая мапперы | заголовки `X-Gateway-*`, тело ответа - обычный chat completion | приложение уже умеет парсить chat completion, трогать эту часть не нужно |
| Что делать, если выходной гейт сработал в потоке уже после того, как заголовки ушли | отдельное SSE-событие перед `[DONE]` (раздел 8.1) | заголовки физически нельзя переслать заново - это не баг реализации, а свойство HTTP |
| Показывать ли оговорку про возможный обрыв над каждым сообщением | нет, только когда обрыв реально случился | предупреждение, которое висит всегда, за день перестают читать - вместе с ним перестают замечать настоящее |
| Какой дефолт у режима стрима | `buffer` | первое число (12 знаков) было свойством одного промпта, не общим правилом; решение принято только после замера по всем категориям выходного гейта |
| Как ловить ссылки-угрозы без белого списка доменов | признаки эксфильтрации (сырой IP, сокращатель, исполняемый файл, вложенный адрес, длинный query-параметр) вместо домена | приложение про здоровье ребёнка легитимно даёт ссылки на медицинские организации не из списка провайдера |
| Кто пишет каждый следующий слепой набор | новый, ранее не задействованный человек, без доступа к предыдущим наборам и их результатам | иначе исправление детектора превращается в подгонку под известный ответ |

## 5. Что пошло не по плану

- **28 из 28 на первом прогоне оказалось не результатом, а сигналом проблемы измерения.** В
  контракт task13 деление dev/holdout не попало заранее - это упущение при написании контракта,
  закрыто отдельной ревизией уже по ходу работы, а не с самого начала.
- **Одного слепого набора не хватило.** После первого усиления обнаружилось, что чинить детектор,
  глядя в тот же набор, на котором нашли пропуск, - это подгонка под ответ. Потребовался третий,
  ранее никем не виденный набор, чтобы получить не завышенную цифру.
- **Устранение одного ложного срабатывания породило новый пропуск.** Снятие белого списка доменов
  починило блокировку легитимной ссылки на ВОЗ, но фишинговая ссылка с коротким токеном в параметре
  перестала ловиться - регрессия, а не чистое улучшение. Разбор - `REPORT.md` раздел 6.
- **Первый замер утечки в потоке был неполным и дал ложно оптимистичный вывод.** Двенадцать знаков
  на одной категории («опасная команда») чуть не стали основанием сменить дефолт стрима. Второй,
  более полный замер по всем трём категориям выходного гейта (максимум 815 знаков) этот вывод
  опроверг - решение по дефолту переигран.
- **Детектор выдуманных ключей не сработал ни разу за восемь потоковых прогонов** - хотя вне потока
  (dev-набор) ловит стабильно. Причина не в детекторе: модель за эти восемь попыток не выдала
  подходящую по формату строку. Записано как невоспроизводимость модели, а не как провал детектора.
- **Журнал живого прогона против апстрима не сохранился в `raw/audit/`.** Директория создаётся
  автоматически при первом запросе к серверу, но на диске она пуста - у отчёта по этой части
  измерения нет отдельного raw-артефакта, только запись в рабочем протоколе. Отмечено как
  ограничение, не скрыто.
- **92 автоматических кейса не нашли три дефекта, которые нашёл один ручной прогон в приложении.**
  Экран журнала падал на законно пустом поле статуса при блокировке; секрет, один раз пойманный в
  истории чата, блокировал этот чат навсегда на всех следующих сообщениях; приложение писало сырой
  текст запроса (включая почту и номер карты) в лог устройства при уровне логирования `ALL`. Все три
  - не про детекторы и не про одно сообщение, а про стык приложения с сервером и про
  последовательность сообщений в одном чате - то, что 92 изолированных кейса структурно не проверяют.
  Все три починены, второй ручной прогон подтвердил фиксы на живом журнале шлюза
  (`raw/audit/gateway-20260805.jsonl`). Разбор - `REPORT.md` раздел 10.
- **Сценарий ручной проверки сначала не учёл собственный роутинг из task10.** Первый пробный вопрос
  про температуру не дошёл до шлюза - его перехватил локальный классификатор и ответил без сети.
  Пришлось подобрать вопрос, который точно уходит в облако.

## 6. Открытые концы

- **Правка регрессии по фишинговой ссылке (класс 7) сделана после замера и не переизмерялась.**
  Порог длины query-параметра остаётся тем же, что дал пропуск на `holdout_cases.jsonl.b64` - свежего
  прогона, подтверждающего, что фишинговый кейс теперь ловится, нет.
- **`harness/spec13.py` продолжил меняться после того, как все текущие `results/*.json` были сняты**
  (в коде уже есть третья ревизия - детектор JWT, класс 4 - которой нет ни в `GATEWAY_CONTRACT.md`,
  ни в dev-наборе, ни в замере по `holdout2_cases.jsonl.b64`, где семья `jwt_token` числится пропущенной
  0 из 1). Цифра по этой правке будет другой задачей - здесь её нет.
- **Ограничение по частоте держится на IP клиента.** За эмулятором и прокси все клиенты выглядят
  одним адресом - защищает шлюз от перегрузки, но не разделяет пользователей. Честное разделение
  требует ключа клиента, которого в задании нет.
- **Живой прогон против апстрима - четыре сценария, не полный охват.** Он подтверждает, что шлюз
  физически работает (ключ не уходит на клиент, блокировка не пускает запрос наверх, лимит частоты
  срабатывает), но не измеряет качество детекторов - для этого нужны как раз три набора кейсов из
  раздела 3.
- **Косметический дефект после ручного прогона, чинится отдельно.** Код причины `secret_in_history`
  (раздел 6.1 контракта, введён по итогам ручного прогона) не заведён в словаре подписей приложения -
  пользователь видит «неизвестная причина» вместо человекочитаемого текста. Само решение (маска, а не
  блок) работает правильно, страдает только подпись в интерфейсе.
