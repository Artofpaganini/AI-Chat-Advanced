# Контракт шлюза

Заморожен до начала работы. Обе стороны - сервер на Python и приложение на Kotlin - пишутся по этому
документу и не договариваются между собой иначе. Меняется только через раздел «Ревизии» с датой.

---

## 1. Зачем нужен шлюз, если в приложении уже есть защита

В приложении после task11 и task12 есть входной и выходной guard. Разведка показала, чего в них нет
и почему сетевой рубеж всё равно нужен.

| Что | В приложении | В шлюзе |
|---|---|---|
| детект секретов - ключи, токены, приватные ключи | **нет ни одного регекса** | есть |
| PII на входе - почта, телефон, карта | нет, проверяется только ответ модели | есть |
| проверка карты по Луну | нет, любые 13-19 цифр считаются картой | есть |
| можно ли отключить | **да, флажком в настройках** | нет, клиент на это не влияет |
| аудит решений | нет, только счётчики в интерфейсе | журнал в файле |
| ключ провайдера | лежит в приложении | лежит только на шлюзе |
| ограничение частоты | нет | есть |
| учёт стоимости | нет | есть |

Главная строка здесь - предпоследняя в первой половине таблицы. Клиентский guard выключается
переключателем, значит защитой от злоумышленника он не является по устройству. Шлюз - является.

## 2. Что шлюз слушает

Адрес по умолчанию `http://127.0.0.1:8091`. Порт выбран рядом с уже занятыми: 8080 - локальная
модель, 8090 - triage-сервер task7. Android-эмулятор видит хост как `10.0.2.2`, поэтому в приложении
адрес шлюза `http://10.0.2.2:8091/v1/`.

| Метод и путь | Что делает |
|---|---|
| `POST /v1/chat/completions` | основной путь: проверка, проксирование наверх, проверка ответа |
| `GET /gateway/audit?limit=N` | последние N записей журнала, для экрана в приложении |
| `GET /gateway/stats` | сводка: число запросов, блокировок, маскирований, токенов, денег |
| `GET /gateway/health` | живой или нет, плюс адрес апстрима и режим гейтов |

Тело `POST` - обычный запрос chat completion. Шлюз не меняет его форму: поля `model`, `messages`,
`stream`, `temperature`, `max_tokens`, а также нестандартные `adapters`, `repetition_penalty`,
`reasoning_effort` идут наверх как есть.

### 2.1 Форма ответа служебных эндпоинтов

Изначально в контракте был описан только формат файла журнала, но не форма HTTP-ответа. Из-за этого
приложение писалось с гадательным разбором и запасными вариантами ключей. Дыра закрыта, форма снята
с живого сервера и зафиксирована:

```
GET /gateway/health
{"status": "ok", "upstream": "...", "input_guard": true, "output_guard": true,
 "stream_guard": "buffer", "rate_limit_per_minute": 20, "key_present": true}

GET /gateway/stats
{"requests_total": 0, "by_verdict": {}, "masked_count_total": 0,
 "tokens_in_total": 0, "tokens_out_total": 0, "cost_usd_total": 0.0, "avg_latency_ms": 0}

GET /gateway/audit?limit=N
{"items": [ <записи журнала, поля из раздела 10> ], "count": 0}
```

Список записей лежит под ключом `items`, а не в корне массивом. `by_verdict` - словарь вердикт-число,
ключи те же, что в разделе 4.

## 3. Ключ

Приложение **не отправляет** заголовок `Authorization`. Ключ читается шлюзом через
`llm_client.read_api_key` - сначала переменная окружения `DEEPSEEK_API_KEY`, потом `local.properties`.
Шлюз подставляет его сам при обращении наверх.

Это не деталь настройки, а смысл задачи: секрет уезжает с клиента.

Если приложение всё же прислало `Authorization`, шлюз его игнорирует и **не логирует**.

## 4. Заголовки ответа - канал сигналов в приложение

Тело ответа остаётся обычным chat completion, чтобы мапперы приложения не переписывались. Всё, что
шлюз хочет сказать о своей работе, едет в заголовках.

| Заголовок | Значения | Смысл |
|---|---|---|
| `X-Gateway-Verdict` | `pass` · `masked` · `blocked_input` · `blocked_output` · `rate_limited` | что случилось с запросом |
| `X-Gateway-Reasons` | список через запятую, например `api_key,card` | какие детекторы сработали |
| `X-Gateway-Masked-Count` | целое | сколько фрагментов замаскировано |
| `X-Gateway-Tokens-In` / `X-Gateway-Tokens-Out` | целые | токены по данным апстрима, при блокировке нули |
| `X-Gateway-Cost-Usd` | число с шестью знаками | стоимость запроса |
| `X-Gateway-RateLimit-Limit` / `X-Gateway-RateLimit-Remaining` | целые | лимит в минуту и остаток |
| `X-Gateway-Request-Id` | строка | сквозной идентификатор, он же ключ записи в журнале |

Причины в `X-Gateway-Reasons` - только коды детекторов из раздела 6. **Сам найденный секрет в
заголовок не попадает никогда.**

## 5. Коды ответа

| Ситуация | Код | Тело |
|---|---|---|
| всё чисто, ответ модели прошёл | `200` | ответ апстрима как есть |
| секреты замаскированы, запрос ушёл наверх | `200` | ответ апстрима как есть |
| входной гейт заблокировал | `200` | **валидный chat completion**, где текст ответа - предупреждение пользователю |
| выходной гейт заблокировал | `200` | валидный chat completion с текстом-заменой |
| превышена частота | `429` | тело с полем `error`, плюс заголовок `Retry-After` |
| апстрим не ответил или вернул ошибку | код апстрима | тело апстрима без изменений |

Почему блокировка приходит с кодом `200`, а не `403`: приложение при ошибке HTTP показывает
техническое сообщение об ошибке сети, и человек видит «что-то сломалось» вместо объяснения. С кодом
`200` и вердиктом в заголовке приложение показывает нормальный текст и баннер над ним. Ограничение
частоты - исключение, там `429` уместен, потому что это действительно отказ обслуживания.

## 6. Детекторы входа

Коды фиксированы, приложение отображает их по этому списку.

| Код | Что ловит | Политика по умолчанию |
|---|---|---|
| `api_key_openai` | `sk-`, `sk-proj-` и следом достаточная длина | маска |
| `api_key_anthropic` | `sk-ant-` | маска |
| `github_token` | `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_` | маска |
| `aws_access_key` | `AKIA`, `ASIA` плюс 16 знаков | **блок** |
| `aws_secret_key` | 40 знаков base64 рядом со словом secret | **блок** |
| `private_key_pem` | `-----BEGIN ... PRIVATE KEY-----` | **блок** |
| `generic_bearer` | `Bearer ` плюс длинный токен | маска |
| `card` | 13-19 цифр, **прошедшие проверку Луна** | маска |
| `email` | обычный адрес почты | маска |
| `phone` | телефон в международном или местном виде | маска |
| `base64_secret` | строка base64, внутри которой после раскодирования нашёлся любой секрет выше | **блок** |
| `split_secret` | префикс ключа, разорванный склейкой или переносом | маска |

Разделение на маску и блок не случайно. Маскируется то, без чего запрос сохраняет смысл: почта,
телефон, карта, пользовательский ключ. Блокируется то, что означает утечку доступа к инфраструктуре -
ключи AWS и приватные ключи. Их маскировать бессмысленно: если такое попало в поле ввода, разговор
надо остановить, а не продолжать с дыркой в тексте.

Маска имеет вид `[REDACTED_API_KEY]`, `[REDACTED_CARD]`, `[REDACTED_EMAIL]`, `[REDACTED_PHONE]` -
по одной на категорию, а не одна общая. Пользователь по маске понимает, что именно вырезали.

**Проверяются все сообщения запроса, а не только последнее.** Секрет, лежащий в третьем сообщении
истории, уходит наверх точно так же, как из последнего.

### 6.1 Новое сообщение и история - разные вещи, добавлено 2026-08-05

Прогон на эмуляторе вскрыл дефект, которого не видно ни в одном автоматическом наборе. После
сообщения с ключом AWS **каждый следующий запрос в том же чате блокировался**, потому что история
уходит наверх целиком и блокирующий детектор срабатывал снова и снова. Баннер при этом писал «в
сообщении обнаружены данные», хотя триггер лежал на несколько ходов выше. Выхода из этого состояния
у пользователя не было - только новый чат, о чём интерфейс не сообщал.

Причина в том, что политика не различала два разных случая. Различаем:

| Где найден секрет | Что делаем | Почему |
|---|---|---|
| в новом сообщении пользователя | как в разделе 6 - блок или маска | пользователь прямо сейчас пытается отправить секрет, его надо остановить |
| **только в старых сообщениях истории** | **всегда маска, никогда блок** | это уже случилось, наверх секрет всё равно не уйдёт под маской, а блокировать человека за прошлое - значит сломать ему чат навсегда |

Правило одной строкой: блок останавливает **действие**, а не наказывает за **состояние**. История - это
состояние, и его надо чинить маской, а не отказом.

Вердикт в таком случае - `masked`, причины перечисляются, но в них добавляется признак, что
сработало на истории, чтобы приложение могло сказать об этом человеческим языком.

Код этого признака - **`secret_in_history`**. Он не детектор и не имеет своей политики. Приложение
обязано иметь для него подпись, иначе человек увидит «неизвестная причина» и пойдёт искать секрет в
сообщении, которое только что отправил, - а его там нет.

**Исправление 2026-08-05, найдено заказчиком при первой же проверке.** Сначала признак ставился
только при понижении блока до маски. Это неверно: у почты, телефона и карты политика и так маска,
понижать нечего, поэтому признак не ставился вовсе. Человек получал баннер «замаскировали почту и
карту» на запрос, где он ничего подобного не писал, и шёл искать несуществующее в своём последнем
сообщении.

Правило теперь простое и не зависит от политики детектора: **если все находки лежат только в истории
и ни одна не задевает новое сообщение - признак `secret_in_history` ставится всегда.** Понижали блок
или нет - неважно, человеку нужно знать, где именно нашлось.

## 7. Детекторы выхода

| Код | Что ловит |
|---|---|
| `generated_secret` | модель выдала строку, похожую на настоящий ключ |
| `system_prompt_leak` | в ответе два и более маркера системного промпта, либо один длиннее 40 знаков |
| `suspicious_url` | ссылка на адрес не из белого списка, особенно с данными в параметрах |
| `dangerous_command` | `curl ... \| sh`, `rm -rf`, `chmod 777`, `eval`, `base64 -d \| bash` и подобное |
| `pii_echo` | в ответе появилась почта, телефон или карта, которых не было во входных данных |

Маркеры системного промпта берутся **из одного места** - файла констант шлюза, синхронизированного с
`DeepSeekDefaults`. В приложении эта ошибка уже допущена: `OutputGuardMapper` дублирует литералы, и
при правке промпта они разъедутся. Повторять её нельзя.

## 8. Потоковый ответ и выходной гейт

Настоящий конфликт: проверить ответ можно только когда он собран, а стрим по определению отдаёт
частями. Делаем два режима, оба меряем.

| Режим | Как работает | Чем платим |
|---|---|---|
| `buffer` (по умолчанию) | шлюз копит ответ апстрима целиком, проверяет, потом отдаёт одним потоком | пользователь ждёт весь ответ, эффект печатающей машинки теряется |
| `incremental` | чанки идут сразу, шлюз проверяет накопленное на каждом чанке и обрывает поток при срабатывании | начало утечки уже ушло к пользователю |

### 8.2 Сколько именно утекает - замер от 2026-08-05

Первый замер дал двенадцать знаков до обрыва, и из этого был сделан вывод, что `incremental` можно
ставить дефолтом. Вывод оказался преждевременным: двенадцать знаков были свойством промпта, где
`curl http://` стоял в первом же слове ответа.

| Категория | Знаков до обрыва, медиана | Максимум |
|---|---|---|
| опасная команда | 12 | 12 |
| эхо персональных данных | 546 | 546 |
| утечка системного промпта | **732** | **815** |

Величина утечки определяется не режимом, а тем, как далеко от начала ответа стоит признак, по
которому срабатывает гейт. Утечка системного промпта опознаётся только когда наберутся два маркера -
к этому моменту у пользователя почти вся страница текста.

**Дефолтом остаётся `buffer`.** `incremental` допустим там, где задержка важнее полноты защиты, но
включать его молча нельзя - пользователь должен знать, что часть текста он увидит до среза.

Отдельно зафиксировано: детектор выдуманных ключей не сработал ни разу за восемь потоковых прогонов,
хотя вне потока ловит стабильно. Модель за эти восемь попыток не выдала подходящую строку. Это
невоспроизводимость модели, а не результат по детектору, и в отчёте это записано именно так, а не
нулём в таблице.

Разница по задержке до первого символа замеряется и попадает в отчёт числами. Выбор режима - флаг
запуска `--stream-guard`.

### 8.1 Как приложение узнаёт об обрыве - добавлено 2026-08-05

Заголовки ответа уходят **до** тела. Значит вердикт выходного гейта в них попасть не может: в
`X-Gateway-Verdict` остаётся входной вердикт, даже если поток потом оборвали. Это свойство HTTP,
чинить его нечем.

Первое предложенное решение - показывать в приложении оговорку над каждым сообщением - отклонено.
Предупреждение, которое висит всегда, перестают читать, и вместе с ним перестают замечать настоящее.

Правильное решение - сказать приложению правду отдельным событием. При срабатывании выходного гейта
в режиме `incremental` шлюз **перед закрытием потока** отправляет последним событием:

```
data: {"gateway_output_verdict": "blocked_output", "gateway_output_reasons": ["dangerous_command"], "gateway_truncated_at_chars": 12}
```

и только потом `data: [DONE]`.

Поле `gateway_truncated_at_chars` - сколько знаков успело уйти к пользователю до обрыва. Оно нужно не
для красоты: это измеренная цена режима, и пользователь имеет право знать, что часть текста он уже
увидел.

Приложение показывает баннер **только когда пришло это событие или когда вердикт в заголовке не
`pass`**. В остальных случаях никакого баннера нет - есть строка со стоимостью и токенами, которой
достаточно, чтобы понять, что запрос шёл через шлюз.

## 9. Ограничение частоты

Скользящее окно 60 секунд, ключ - IP клиента. По умолчанию 20 запросов в минуту, меняется флагом
`--rate-limit`. Превышение - `429`, заголовок `Retry-After` с числом секунд до освобождения слота.

Оговорка, которая пойдёт в отчёт: за эмулятором и прокси все клиенты выглядят одним IP, поэтому
ограничение по IP в такой постановке защищает шлюз от перегрузки, но не разделяет пользователей.
Честное разделение требует ключа клиента, которого в задании нет.

## 10. Журнал аудита

Формат JSONL, одна строка на запрос, файл `raw/audit/gateway-YYYYMMDD.jsonl`.

| Поле | Что внутри |
|---|---|
| `ts` | время в ISO |
| `request_id` | тот же, что в заголовке ответа |
| `client_ip` | адрес клиента |
| `model` | модель из запроса |
| `verdict` | как в заголовке вердикта |
| `input_reasons` | коды сработавших входных детекторов |
| `output_reasons` | коды сработавших выходных детекторов |
| `masked_count` | сколько фрагментов замаскировано |
| `messages_hash` | хеш текста запроса, чтобы сверять повторы без хранения самого текста |
| `prompt_preview` | первые 200 знаков **уже замаскированного** текста |
| `tokens_in`, `tokens_out`, `cost_usd` | учёт стоимости |
| `latency_ms` | полное время, включая апстрим |
| `upstream_status` | код ответа апстрима |

**Запрещено класть в журнал:** найденный секрет в любом виде, заголовок `Authorization`, полный текст
ответа модели. Проверка этого запрета - часть гейта отчёта, а не пожелание.

## 11. Учёт стоимости

Токены берутся из поля `usage` ответа апстрима. Если апстрим их не вернул, считается оценка по длине
текста, и запись помечается флагом `tokens_estimated`. Тарифы берутся из существующего спека прошлых
задач, где они уже заданы, а не выдумываются заново.

При блокировке на входе стоимость ноль - наверх ничего не ушло. Это отдельная измеряемая величина:
сколько денег сэкономил входной гейт.

---

## 12. Что считается успехом задачи

| Метрика | Как считаем |
|---|---|
| поймано секретов | доля тест-кейсов с секретом, где сработал верный детектор |
| ложные срабатывания | доля чистых кейсов, ошибочно заблокированных или замаскированных |
| пропуски | список кейсов, где секрет прошёл, с разбором почему |
| задержка шлюза | время шлюза минус время апстрима, отдельно для двух режимов стрима |
| экономия | сколько запросов не ушло наверх и сколько это стоило бы |

Ложные срабатывания важнее пропусков для впечатления от продукта: гейт, режущий здоровые сообщения,
выключат в первый же день, и защиты не станет вовсе.

## 13. Тест-кейсы

Не менее десяти, фактически больше. Обязательные из задания: ключ AWS, номер карты, секрет в base64,
секрет, разорванный на части, чистый промпт без секретов.

Добавляем от себя те, что проверяют не детектор, а **измеритель**:

- карта, не проходящая проверку Луна - не должна ловиться
- медицинский текст с числами - вес, рост, даты, дозировки - не должен выглядеть картой
- сам текст-предупреждение шлюза, поданный на вход - не должен считаться атакой
- секрет в середине истории, а не в последнем сообщении

Все ключи в тест-кейсах **поддельные**. Настоящий ключ в тестовых данных - это тот самый инцидент,
который задача призвана предотвращать.

## 15. Ревизии

### Ревизия 2026-08-05 - деление набора на dev и holdout

**Причина.** Первый прогон дал 28 из 28, ноль пропусков, ноль ложных срабатываний. Такие числа
означают не качество детектора, а то, что набор писал тот же, кто писал детектор. Он проверил свою
работу на данных, подогнанных под свою же работу.

В task11 и task12 для этого вводилось деление `dev` и `holdout` семьдесят на тридцать. В контракт
task13 оно не попало - упущение автора контракта, а не исполнителя.

**Что меняется.**

`data/cases.jsonl.b64` остаётся набором `dev`. Он писался со знанием кода и годится для отладки, но
цифры по нему в отчёт как результат защиты **не идут**.

Появляется `data/holdout_cases.jsonl.b64`. Правила его создания:

- пишет другой исполнитель, **не читая `harness/` вообще** - ни детекторов, ни спека, ни dev-набора
- он не знает списка кодов детекторов из раздела 6, поэтому кейс не содержит `expect_reasons`
- вместо кодов кейс несёт `expect_caught: true|false` и `what` - человеческое описание, что спрятано
- оценка простая: сработал хоть один детектор или нет, и был ли он должен сработать

**Главная цифра отчёта - результат по `holdout`.** По `dev` числа приводятся отдельной строкой с
пометкой, что набор писался со знанием реализации.

Ожидание, записанное до прогона: на `holdout` результат будет заметно хуже 28 из 28. Если он окажется
таким же - это повод искать ошибку в измерителе, а не радоваться.

**Результат.** 14 из 31, одно ложное срабатывание из 11 чистых. Ожидание подтвердилось: 28 из 28
измеряли качество набора, а не качество фильтра.

### Ревизия 2026-08-05, вторая - второй слепой набор

**Причина.** Пропуски на первом слепом наборе делятся на два разных сорта, и обращаться с ними надо
по-разному.

Часть - **законные пробелы покрытия**: в фильтре просто нет паттернов под форматы Stripe, Slack,
Telegram, SendGrid, GitLab, Azure, нет декодирования hex, нет склейки сообщений. Закрывать их надо,
это очевидная недоделка, а не подгонка.

Часть - **классы обхода**: разворот строки, посимвольная разрядка, числительные словами. Тут тоже
нужна работа, но результат обязан проверяться заново.

**Правило исправления.** Чинится **класс**, а не кейс. Исполнитель, который усиливает детекторы, не
читает ни `holdout_cases.jsonl.b64`, ни `results/holdout_tests.json` - он получает от координатора
описание классов словами. Иначе получится подгонка под известные ответы, а цифра «после» окажется
такой же пустой, как 28 из 28.

**Проверка.** Появляется `data/holdout2_cases.jsonl.b64` - второй слепой набор от третьего исполнителя,
который не видел ни кода, ни обоих предыдущих наборов. Цифра «после» берётся **только** с него.

Результат по первому слепому набору после усиления тоже приводится, но с прямой пометкой: этот набор
уже участвовал в разборе, и число по нему завышено по построению.

**Результат.** Первый слепой набор 26 из 31, второй 25 из 36, ложных ноль на обоих. Разрыв
84 процента против 69 - измеренная цена подгонки под первый набор.

### Ревизия 2026-08-05, третья - правки после замера

Записана отдельно, потому что сделана **после** того, как сняты все числа, и ни одним слепым набором
не проверена. Так и должна читаться: код здесь ушёл вперёд замера.

| Что добавлено | Почему |
|---|---|
| признак фишинга: внешняя ссылка плюс рядом побуждение ввести карту, код или пароль | закрытие регрессии - убрав белый список доменов, потеряли фишинговую ссылку с коротким параметром |
| диапазоны длин вместо точных в паттернах ключей | ключ на один знак короче эталона не ловился |
| нормализация похожих символов распространена на паттерны ключей | раньше работала только для почты и телефона, подмена буквы ломала поиск ключа |
| детектор JWT | три части через точку, точка рвёт поиск base64-кандидата в принципе |
| порог url-кодирования снижен до одной последовательности | при точечном двойном кодировании настоящая последовательность одна |

Третьего слепого набора не заводили сознательно. Цикл «починил - замерил - починил» не имеет конца,
а каждый новый набор стоит отдельной работы. Цифра 69 процентов снята до этих правок и остаётся
результатом задачи. Правки сделаны по существу дефектов, а не ради метрики - именно поэтому их можно
не переизмерять, но нельзя выдавать за улучшение результата.

**Контрольный прогон после всех правок дал 29 из 36, то есть 81 процент.** Эту цифру нельзя ставить
вместо 69, и вот почему.

Исполнитель, который правил детекторы, второй слепой набор действительно не открывал - запрет
соблюдён. Но классы для правок - JWT, двойное кодирование, точные длины, нормализация ключей -
координатор взял из разбора пропусков **по этому самому набору** и передал словами. Набор не был
прочитан исполнителем, но был прочитан координатором, и знание всё равно просочилось.

Это тот же механизм, что завысил первый слепой набор с 45 до 84 процентов. Утечка через посредника -
такая же утечка. Признать её честнее, чем радоваться восьмидесяти одному проценту.

Итог: **69 процентов - результат задачи**, 81 процент - цифра после правок на уже разобранном наборе.
