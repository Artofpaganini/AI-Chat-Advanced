# Task13 - шлюз к LLM

HTTP-прокси между приложением и DeepSeek: снимает ключ провайдера с клиента, проверяет запрос до
того, как он уйдёт наружу, и ответ модели до того, как он попадёт к пользователю, ограничивает
частоту запросов, ведёт журнал аудита и учёт стоимости.

**Главный результат:** честная цифра защиты - **69%** пойманных секретов и опасного вывода на
третьем слепом наборе кейсов, который не видел никто из тех, кто чинил код. Разрыв с 84% на первом
слепом наборе (уже участвовавшем в разборе пропусков) - 15 процентных пунктов, это измеренная цена
подгонки под известные ошибки. Числа по dev-набору (64 из 64) не значат ничего - его писал тот же
человек, что писал детекторы. Подробности - `RESULT.md`.

Главная цель задачи - убрать ключ провайдера с клиента - выполнена и подтверждена живым прогоном
против настоящего сервера DeepSeek.

Отдельно шлюз дважды прогнали руками в приложении на Android-эмуляторе. Первый прогон нашёл три
дефекта, которые не увидел ни один из 92 автоматических кейсов - все три на стыке приложения с
сервером и на последовательности сообщений в одном чате, не в детекторах. Второй прогон, после
починки, подтвердил все три фикса на живом журнале шлюза. Подробности - `REPORT.md` раздел 10,
человеческим языком - `RESULT.md` раздел 7.

## Наборы кейсов закодированы

Файлы в `data/` лежат как `*.jsonl.b64`, а не открытым текстом `*.jsonl`. Причина - сканер секретов
GitHub при пуше принимает синтетические ключи в тестовых кейсах (AWS access key, Stripe secret key
и похожие) за настоящие и блокирует push protection. Ключи в наборах поддельные с самого начала
(канонические примеры из документации вроде `AKIAIOSFODNN7EXAMPLE` или явно синтетические строки),
но сканер, как и наш собственный детектор, различает их только по формату - не по факту
реальности. Портить формат ключей нельзя: тогда детекторы проверялись бы на данных, которых в
жизни не бывает, и замер потерял бы смысл.

Кодирование построчное base64 (`harness/case_codec.py`) - каждая строка исходного `.jsonl`
превращается в одну строку base64, один в один, без потерь. `run_tests.py` декодирует файл перед
разбором JSON, дальше всё работает как раньше - детекторы получают ту же самую строку, что и до
кодирования. Это подтверждено побайтовым сравнением декодированного файла с оригиналом перед тем,
как оригиналы были удалены.

Посмотреть набор глазами:

```bash
python3 harness/show_cases.py data/holdout_cases.jsonl.b64
```

**Кодирование - не защита.** Это способ не спорить со сканером секретов на формате, а не скрыть
что-то настоящее. Ключ провайдера (`DEEPSEEK_API_KEY`) в `data/` никогда не хранился и здесь тоже
не хранится - см. раздел «Что важно знать» ниже.

## Требования

- Python 3.9, только стандартная библиотека. Внешних пакетов нет и не нужно - весь репозиторий
  собран так же во всех предыдущих задачах.
- Ключ `DEEPSEEK_API_KEY` - в окружении либо в `local.properties` в корне репозитория. Читается
  через `llm_client.read_api_key`, шлюз подставляет его сам - клиент заголовок `Authorization` не
  отправляет и не может, даже если попробует.
- Сеть нужна только для живых прогонов (`gateway_server.py` против апстрима,
  `bench_stream.py` без `--dry-run`). Прогон тест-наборов (`run_tests.py`) работает целиком локально,
  без единого запроса.

## Команды

Всё запускается из каталога задачи.

```bash
cd challenge_advanced/task13

# план прогона тест-набора: сколько кейсов, без единого запроса к API
python3 harness/run_tests.py --dry-run

# прогон по dev - не результат защиты, только проверка, что код делает то, что задумал автор
python3 harness/run_tests.py --cases data/cases.jsonl.b64 --out results/guard_tests.json

# прогон по первому слепому набору
python3 harness/run_tests.py --cases data/holdout_cases.jsonl.b64

# прогон по второму слепому набору - главная цифра отчёта
python3 harness/run_tests.py --cases data/holdout2_cases.jsonl.b64

# поднять сам шлюз локально (нужен DEEPSEEK_API_KEY)
python3 harness/gateway_server.py --stream-guard buffer

# план замера задержки/утечки стрима: сколько вызовов к апстриму и оценка стоимости, без запросов
python3 harness/bench_stream.py --dry-run

# замер задержки buffer/incremental против апстрима, 5 повторов на сценарий
python3 harness/bench_stream.py --repeats 5

# замер утечки по трём категориям выходного гейта отдельно, дописывает results/stream_bench.json
python3 harness/bench_stream.py --leak-categories --repeats 8
```

`run_tests.py` возвращает код 1, если гейт целостности провален - но только для dev-набора. Плохой
результат на `holdout`/`holdout2` - это факт отчёта, а не повод ронять сборку, гейт на них не
действует нарочно.

## Что важно знать

- **Три набора кейсов не равны друг другу.** dev показывает, что код делает задуманное - не больше.
  holdout и holdout2 показывают, ловит ли код то, чего автор не предусмотрел явно. Только holdout2
  не участвовал ни в одном разборе пропусков - это единственная цифра без подгонки.
- **Гипотезы записаны в `SPEC.md` до соответствующих прогонов** и не переписывались задним числом -
  там же вердикты со ссылкой на конкретный файл в `results/`.
- **Числа только из `raw/` и `results/`.** Одно исключение честно названо: скриптовый живой прогон
  A2 против апстрима (`REPORT.md` раздел 5) не оставил отдельного файла - его числа из рабочего
  протокола, не из файла для пересчёта. Ручной прогон в приложении (раздел 10) исключением не
  является - у него есть `raw/audit/gateway-20260805.jsonl`.
- **Автоматические тесты и ручная проверка на устройстве ловят разное.** 92 кейса dev и обоих слепых
  наборов проверяют одно сообщение за раз. Три дефекта, которые нашёл ручной прогон в приложении
  (падение экрана журнала, вечная блокировка чата секретом из истории, секреты в логе устройства),
  жили ровно там, где автоматический набор структурно не смотрит - на стыке приложения с сервером и
  на последовательности сообщений. `REPORT.md` раздел 10, `RESULT.md` раздел 7.
- **Код после сдачи результатов продолжил меняться** (`harness/spec13.py` содержит правку новее
  всех снимков `results/*.json` - детектор JWT, не отражённый ни в контракте, ни в холодных
  замерах). Числа в отчёте - состояние на момент снятия `results/`, не текущее состояние `harness/`.
- **Ключ провайдера не попадает ни в код, ни в журнал, ни в тестовые данные.** Все ключи в
  `data/*.jsonl.b64` заведомо поддельные - канонические примеры из документации
  (`AKIAIOSFODNN7EXAMPLE`) или синтетические строки, помеченные как таковые прямо в кейсе. Файлы
  закодированы построчным base64, чтобы сканер секретов GitHub не принимал их формат за настоящий -
  подробности в разделе «Наборы кейсов закодированы» выше.
