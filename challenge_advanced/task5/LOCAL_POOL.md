# Пул C - 10 простых задач для локальной модели

Модель: `qwen3-coder:30b` на Ollama (локально, без сети).
Харнесс: переиспользован от task4 - `challenge_advanced/task4/harness/agent_loop.py`.
Инструменты у модели: `list_dir`, `search`, `read_file`, `write_file`, `build`.

## Условия прогона

| | |
|---|---|
| Песочница | клон репозитория, реальный проект не трогается |
| Гейт | компиляция `:feature:chat:compileCommonMainKotlinMetadata`, offline |
| Лимиты на задачу | 50 шагов, 40 минут |
| Провал задачи | сборка красная после лимита, либо модель не вызвала ни одного инструмента |
| Между задачами | при провале песочница откатывается, чтобы мусор не тянулся дальше |

Задачи специально простые - размер XS-S, почти все в один-два файла. Смысл замера не в том,
чтобы локальная модель сделала сложное, а в том, чтобы понять, **сколько простых задач подряд она
вытянет** и где сломается.

### Где именно сломалась - и это главный результат

**Все четыре успешные задачи правились в ОДНОМ файле. Провалившаяся требовала четырёх.**

Задача 4 - «показать число сообщений в заголовке» - на вид простейшая, но требует протащить поле
через всю UDF-цепочку: `ChatUiModel` -> `ChatUiMapper` -> `ChatScreen` (+ токен в `ChatDimens`).
Модель тронула все четыре файла, сделала 11 сборок, сожгла 18 тысяч токенов (вдвое больше, чем на
любой другой задаче) и упёрлась в лимит с красной сборкой.

Порог локальной модели проходит не по «сложности задачи» в человеческом смысле, а по **числу файлов,
которые надо держать согласованными одновременно**. Один файл - справляется. Четыре связанных - нет.

### Наблюдения по ходу

- **Не читает ошибку компилятора, а перегенерирует файл целиком.** На первой задаче четыре красных
  сборки подряд, каждый раз файл переписывался с нуля вместо точечной правки по сообщению об ошибке.
- **Не понимает, что задача закончена.** Зелёная сборка на 14-м шаге, работа продолжалась до 27-го.
  Протокол завершения в харнессе есть, модель им не пользуется. Следствие: время упирается в лимит
  шагов, а не в реальную сложность.
- **Дешёвых итераций нет.** 7 сборок на задачу в среднем. Каждая красная сборка - это ещё один полный
  проход генерации файла.

### Наблюдения по ходу

- **Модель не читает ошибку компилятора, а перегенерирует файл целиком.** На первой задаче: четыре

## Сравнение: облако vs локальная модель

| Метрика | Облако, прогон 1 | Облако, прогон 2 | **Локальная `qwen3-coder:30b`** |
|---|---|---|---|
| Задач в пуле | 15 | 15 | 5 |
| Задач подряд без провала | **15/15** | **15/15** | **3** |
| Сделано | 100% | 100% | 80% |
| Среднее на задачу | 7.9 мин | 9.9 мин | **15.2 мин** |
| Сборок на задачу | ~1 | ~1 | **7** |
| Тяжесть задач | XS-M | XS-L | XS-S (специально простые) |
| Точка отказа | **не найдена** | **не найдена** | **найдена: 4-я задача** |

**Прямое сравнение времени некорректно** - у локалки задачи специально проще. Честно сравнивать надо
другое: облако на ЗАМЕТНО более сложном пуле (SSE-стриминг, кросс-платформенные пикеры, рефакторинг
на 200+ строк) ни разу не дошло до точки отказа, а локалка на пуле из однофайловых мелочей сломалась
на четвёртой задаче.

### Что это значит практически

- **Локальная модель применима**, но в узкой нише: правки в пределах одного файла, где есть быстрый
  компилятор-гейт и не жалко 5-10 итераций. Счётчик символов, лимит длины, крестик очистки - сделала.
- **Не применима там, где нужна согласованность нескольких файлов.** А в проекте с UDF почти любая
  осмысленная фича - это цепочка `Model -> Mapper -> Screen`, то есть минимум три файла.
- **Стоимость итерации несопоставима.** Облако: один диспатч, одна сборка. Локалка: 27-42 шага,
  7 сборок, перегенерация файла целиком на каждой ошибке.
- **Главное ограничение не в качестве кода, а в отсутствии стратегии.** Модель не читает ошибку
  компилятора, чтобы починить точечно, и не понимает, что уже закончила. Это лечится не моделью
  побольше, а харнессом: подавать ей diff ошибки, а не весь файл, и жёстко проверять условие выхода.

### Оговорка про честность замера

В середине прогона я запустил gradle в песочнице параллельно с работой модели - это нарушение
правила «не параллелить сборки». Часть красных сборок на первой задаче могла быть следствием моего
вмешательства, а не ошибок модели. Дальше в песочницу не лез, задачи 2-5 замерены чисто.
