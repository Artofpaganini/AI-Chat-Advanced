# Задача 5 - Автономный прогон пула задач

## Что делали

Взяли реальный проект - чат с AI на Kotlin Multiplatform (JarvisChat), завели пул задач в трекере и
запустили ассистента в режиме execution loop: он сам берёт задачу, сам выбирает под неё профиль
(баг / фича / рефакторинг / тесты / доки), делает, прогоняет сборку и тесты, коммитит и берёт
следующую. Пользователь между задачами не вмешивался и промпт не правил. Прогонов вышло три:
первый пул из 15 задач, потом правила доработали по итогам падений и прогнали второй пул из 15
других задач, и отдельно тот же подход прогнали на локальной модели `qwen3-coder:30b` через Ollama.
Всего 35 задач и 344 минуты работы.

## Как решили каждый пункт

| Пункт задания | Как сделано | Где лежит |
|---|---|---|
| Завести 15-20 задач в трекере | Трекер - markdown-файлы в репозитории (задание разрешало текстовый файл). Пул 1 - 15 задач, пул 2 - 15 задач, локальный пул - 10 задач (прогнали 5) | `EXECUTION_LOG.md` (пул 1), `RUN2_LOG.md` (пул 2), `LOCAL_POOL.md` (локальный) |
| Микс: баги, фичи, рефакторинг, тесты, документация | Пул 1: 10 фич + 3 рефактора + 1 тесты + 1 доки, **багов ноль** - это оказалось ошибкой состава. Пул 2: 5 багов + 5 фич + 2 рефактора + 2 теста + 1 доки, все баги подтверждены фактами из кода | таблицы «Пул задач» в `EXECUTION_LOG.md` и `RUN2_LOG.md` |
| Чёткий критерий «сделано / не сделано» | У каждой задачи отдельная колонка «Критерий DONE»: поведение + перечисленные таргеты сборки + точный тест-таск | там же, колонка «Критерий DONE» |
| Ассистент сам выбирает профиль | Колонка «Тип -> профиль» в обоих пулах: `feature` / `bug-fix` / `refactor` / `test` / `docs`. Режим execution loop - надстройка поверх профиля, а не отдельный профиль | `EXECUTION_LOOP_RULES.md`, раздел «Куда это установлено» |
| Задача -> выполнить -> закоммитить -> следующая | Один атомарный коммит на задачу, хеш записан в лог каждой строки | колонка «Коммит» в логах обоих прогонов |
| Автономно, без вмешательства | 0 вмешательств пользователя в обоих облачных прогонах. Сбои цикла закрывались само-восстановлением оркестратора | метрики в `EXECUTION_LOG.md`, `RUN2_LOG.md` |
| Метрика: сколько задач подряд без вмешательства | Прогон 1 - 15 из 15, прогон 2 - 15 из 15, локальная модель - 3 подряд | таблицы «Метрики прогона» |
| Метрика: на какой задаче сломался и почему | Облако **не сломалось ни разу** - пул кончался раньше. У локальной модели точка отказа найдена: задача 4 | `REPORT.md`, раздел «Чего два прогона не выяснили»; `local_results.json` |
| Метрика: среднее время на задачу | 7.9 мин / 9.9 мин / 15.2 мин. Считалось по таймстампам коммитов, не на глаз | таблицы метрик |
| Метрика: процент с первого раза | 86.7% / 60% / 80%. «С первого раза» = ноль автофиксов | таблицы метрик |
| Усиление: доработать правила и прогнать заново | Из падений прогона 1 выведено 12 правил, они вписаны в контракт и гейты, прогон 2 шёл уже по ним. Итоговый свод - 22 правила, у каждого указано, каким падением куплено | `EXECUTION_LOOP_RULES.md` |
| Сравнение первый прогон против второго | Таблица по 9 метрикам + разбор, почему прямое сравнение цифр некорректно (пулы разной тяжести) | `RUN2_LOG.md`, раздел «Сравнение»; `REPORT.md` |
| Тот же пул на локальной модели | Отдельный прогон `qwen3-coder:30b`, песочница-клон, гейт - компиляция. Скрипт-раннер и сырые метрики сохранены | `local_pool_run.py`, `local_results.json`, `LOCAL_POOL.md` |

## Что получилось, а что нет

### Получилось

- **Два облачных прогона по 15 задач подряд без единого вмешательства.** Ноль остановок, ноль
  вопросов пользователю, ноль правок промпта между задачами.
- **Правила реально сработали.** Инциденты дисциплины упали вдвое (4 -> 2), хотя задачи во втором
  пуле были заметно тяжелее: SSE-стриминг, кросс-платформенные пикеры файлов, два рефакторинга по
  200+ строк.
- **Самая крупная задача обоих прогонов (стриминг ответа, размер L) прошла без паузы** - 18 минут,
  2 автофикса, 23 новых теста.
- **Разведка впереди исполнителя окупилась прямо.** Отдельный read-only агент переразмерил 4 задачи
  из 15 ещё до диспатча (одну с M на L), нашёл латентный баг вне задания и шесть побочных дефектов.
- **У локальной модели найдена честная точка отказа** и понятно, чем она задана - числом файлов,
  а не сложностью задачи.

### Не получилось

- **Точка отказа облака не найдена ни разу.** Оба пула закончились раньше, чем ассистент потерял
  управляемость. Метрика «сколько продержится без паузы» упёрлась в длину пула, а не в предел
  системы. Доказано только: предел дальше 15 задач подряд. Для настоящего замера нужен пул на 40-50.
- **Сравнение «насколько дольше продержался второй прогон» не измеримо.** Оба дали 15/15, разницы
  в стойкости нет по построению эксперимента.
- **Прогон 1 отрапортовал 15/15 поверх мёртвого продукта.** Внешний API снял модель `deepseek-chat`,
  приложение не отвечало ни на одно сообщение, а гейт из сборки и моков этого не видит по устройству.
  Нашёл пользователь, а не прогон.
- **После прогона 2 пользователь за минуту нашёл три бага** - и все три оказались регрессиями внутри
  самого пула. Markdown-рендер (задача 9) сломал озвучку: TTS начал зачитывать разметку вслух.
  Стриминг (задача 10) сломал скролл вниз. Каждая фича по отдельности работала, все гейты зелёные.
- **`BUILD SUCCESSFUL` дважды соврал.** Один раз build cache отдал стухший слепок: таск зелёный,
  класс не скомпилирован, тесты не запускались вообще. Другой раз корректный код прошёл 347 тестов
  и не работал - фикс скролла при клавиатуре.
- **Локальный пул урезан с 10 задач до 5** по решению пользователя, задачи 6-10 не гонялись
  (файл `.local_task_prompt.md` остался на задаче 6 - на ней прогон и остановили).
- **Замер локальной модели не полностью чистый:** в середине прогона в песочнице параллельно
  запускался gradle, часть красных сборок первой задачи могла быть следствием этого. Задачи 2-5
  замерены чисто.
- **iOS проверен только компиляцией** - Xcode-проекта в репозитории нет. Поведение стриминга на
  wasmJs живьём тоже не проверялось.

### На чём именно ломался loop

Главное наблюдение: **ломались не задачи, а дисциплина цикла.** Ни одна из 30 облачных задач не
провалилась по причинам, которые предлагало фиксировать задание - «не понял контекст», «выдал
нерабочий код», «зациклился».

| Прогон | Что сломалось | Почему | Чем закрыли |
|---|---|---|---|
| 1, задача 8 | ход завершился без вызова инструмента | громоздкий Bash: heredoc и многострочный commit в одном вызове | дробить: одна команда - одна операция |
| 1, задача 10 | сабагент выполнил `git stash -u` на общем дереве | запрет был без альтернативы, агент обошёл его, решая по сути верную задачу | запрет всегда с альтернативой |
| 1, задача 10 | git-проверка дала ложную пустоту при 9 правках | отфильтрованный вывод `git status` | только сырой `git status --porcelain` |
| 1, задача 10 | агент ушёл чинить чужие 8 падений | гейт задан зонтичным таском `allTests` | точный таск модуля + список pre-existing падений |
| 1, задача 12 | не собран iOS | таргет не был назван в критерии DONE. Дыра в контракте, не в исполнителе | гейт перечисляет все таргеты поимённо |
| 2, задача 1 | похоронил живого агента и передиспатчил, два агента писали одни файлы | пустое рабочее дерево принято за доказательство смерти; агент читал перед записью | нужно доказательство смерти, а не догадка |
| 2, задача 14 | в контракт внесён неверный факт | список «уже покрыто тестами» составлен по памяти, а не grep-ом | любой факт в контракте добывается командой |

Оба инцидента прогона 2 - оркестраторские, а не исполнительские. Исполнители в обоих случаях
оказались точнее: один нашёл тест, который разведка пропустила, другой проверил список и обнаружил,
что он неверен.

### Почему прогон 2 «хуже» по проценту с первого раза

Прямое сравнение здесь некорректно. В первом пуле были тема, типографика и токены отступов - почти
всё это одна-две правки в одном модуле. Во втором - таксономия ошибок через четыре слоя,
SSE-стриминг, `expect/actual` для буфера обмена на три таргета. Падение с 86.7% до 60% - цена
сложности, а не деградация процесса. Честнее смотреть на инциденты дисциплины: они упали вдвое при
вдвое более тяжёлых задачах. И класс автофиксов изменился - в прогоне 2 все шесть это обычные
компиляторные мелочи вроде забытого импорта.

### Локальная модель: где именно сломалась

| # | Задача | Файлов | Итог | Шагов | Сборок | Токенов | Минут |
|---|---|---|---|---|---|---|---|
| 1 | Счётчик символов | 2 | OK | 27 | 8 | 4 190 | 6.0 |
| 2 | Лимит длины сообщения | 2 | OK | 32 | 4 | 5 211 | 6.5 |
| 3 | Крестик очистки поля | 1 | OK | 38 | 9 | 8 903 | 12.6 |
| 4 | **Число сообщений в заголовке** | **4** | **ПРОВАЛ** | 38 | 11 | 18 424 | 41.0 |
| 5 | Плейсхолдер при генерации | 1 | OK | 42 | 3 | 3 659 | 10.0 |

Числа из `local_results.json`. Колонка «файлов» - это фактически изменённые файлы из сырых данных;
в таблице `LOCAL_POOL.md` у задач 1 и 2 стоит 1 файл, потому что там считался основной файл правки,
а вторым шёл `ChatDimens.kt` с константой. На вывод это не влияет.

Всего: 40 387 токенов, 76 минут. Провал задачи 4 - исчерпан лимит шагов при красной сборке.

**Порог локальной модели проходит по числу файлов, которые надо держать согласованными
одновременно.** Все четыре успешные задачи - один-два файла. Провалившаяся требовала четырёх: поле
надо было протащить через всю UDF-цепочку `ChatUiModel -> ChatUiMapper -> ChatScreen`. Модель
сожгла на ней вдвое больше токенов, чем на любой другой задаче.

Два ограничения, которые лечатся харнессом, а не моделью побольше:
1. Не читает ошибку компилятора - на каждой красной сборке перегенерирует файл целиком.
2. Не понимает, что задача закончена: зелёная сборка на 14-м шаге, работа шла до 27-го.

## Что это даёт дальше

1. **Вкладываться надо в гейты и контракты, а не в промпт исполнителя.** Всё, что реально ломало
   loop за 30 задач, лежало именно там: ложно-зелёный кеш сборки, отфильтрованный вывод команды,
   зонтичный тест-таск, неназванный таргет, непроверенный факт в контракте.

2. **Зелёная сборка не доказывает работающий продукт.** Три независимых подтверждения за один день.
   Любой автономный пул, который трогает внешний сервис или UI, обязан хотя бы раз сделать живой
   запрос или смоук на устройстве - иначе loop уверенно рапортует 15/15 поверх мёртвого продукта.

3. **Пул обязан содержать баги, а не только фичи.** Пул без багов не ищет дефектов. Именно поэтому
   мёртвый API прогона 1 не нашёл никто: искать дефекты никого не просили.

4. **На длинном пуле фичи ломают друг друга.** Три регрессии подряд оказались следствием задач того
   же пула. Юнит-тесты взаимодействия фич не видят, ловится только смоуком на собранном продукте.

5. **Локальная модель применима, но в узкой нише** - правки в пределах одного файла, где есть
   быстрый компилятор-гейт и не жалко 5-10 итераций. Всё, что требует согласованности нескольких
   файлов, ей не по силам, а в UDF-проекте почти любая осмысленная фича это минимум три файла.

6. **Свод из 22 правил готов к переиспользованию** - он лежит в `EXECUTION_LOOP_RULES.md`, и у
   каждого правила указано, каким конкретным падением оно куплено. Ни одно не придумано из головы.
