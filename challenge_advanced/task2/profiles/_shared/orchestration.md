# Оркестрация (общее для всех профилей)

## Мейн-агент — оркестратор, не исполнитель
Мейн планирует, раздаёт сабагентам, собирает, проверяет. Руками код не пишет (кроме XS). Контекст мейна
беречь — тяжёлое чтение/поиск/реализацию делегировать. ≤5 одновременных сабагентов.

## Шкала размера и масштаб команды (из `team-lead-orchestration`)
| Размер | Пример | Команда |
|---|---|---|
| **XS** | покрасить кнопку, однострочный баг | session-only: `Explore` + 1 профильный сабагент, без команды |
| **S** | +UseCase/маппер, экран из готовых компонентов | 1-2 сабагента последовательно |
| **M** | кросс-модульная навигация+DI, требования к фиче | `@Architect` → исполнитель → `@Reviewer` |
| **L** | фича 1-2 экрана с нуля, авторизация через API | Architect → Dev(+UI) → Reviewer, SubLead по надобности |
| **XL** | эпик 3+ экранов, миграция, KMP-инфра с нуля | full team + рекурсивные SubLead (глубина 2) |

Алгоритм: **Understand → Evaluate → [Identify platforms] → Decompose → Assign → Formulate → Collect → Verify**.
Формат преамбулы: `📋 Задача · 📊 Сложность · 📱 Платформы(KMM) · 👥 Команда · 📐 План`.

## Консилиум (параллельные эксперты)
На стадиях research/diagnose — несколько сабагентов одним заходом (параллельно), каждый в своём домене
(архитектура / безопасность / данные / UI / DevOps). Оркестратор собирает саммари, синтезирует, при
конфликте — `AskUserQuestion`. Диверсити важнее избыточности: разные линзы, не N одинаковых.

## Persistent-файлы (переживают compaction)
Каждый профиль ведёт файл-состояние в `./swarm-report/<slug>-<profile>.md` (напр. `-reproduce.md`,
`-e2e-scenario.md`, `-plan.md`). Правило: **перед каждым действием перечитать файл**, отмечать сделанные
шаги `[x]`, пропускать выполненное. Итоговый отчёт — `./swarm-report/<slug>-<YYYY-MM-DD>.md`.

## Context-passing между стадиями
В промпт каждого сабагента явно: (1) исходный запрос пользователя, (2) саммари предыдущей стадии,
(3) причина отката (если был). I/O-контракт: что на входе (и что делать, если нет), что на выходе и в
каком формате.

## Переходы стадий
Перед сменой стадии явно писать: `Переход: <текущая> → <следующая>`. Разрешённые переходы — в каждом
профиле (DAG). Все прочие — запрещены (без срезания углов).

## Chaining профилей
Апстрим-профиль по завершении запускает исполнительный, передавая свой артефакт как вход:
`design → feature`, `requirements → architecture|feature`, `architecture → feature|refactor|migration`,
`incident → bug-fix`. Оркестратор явно объявляет: `Chaining: <profileA> → <profileB>`.

## Инструменты (связка)
`ast-index` (поиск кода, watch держит пользователь — не `update`) · `Sentry` (краши/ошибки) ·
`Context7`/DeepWiki (доки/версии, не по памяти) · claude-in-mobile (прокликать UI) · caveman (компактность).
Проектные skills (`<context>-project-context`, `*-udf`, `*-viewmodel`, `compose-principles`) — по контексту.
